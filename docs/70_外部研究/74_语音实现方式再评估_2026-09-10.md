## 1. 产品意图 → 技术要求

**FluentWork 不是语音助手。对话是载体，产物在对话之后**（命中句 → 炼化卡 → 语料库 → 复习）。用户带走的是"更地道的表达"，不是聊天记录。

由此推出的技术要求，按关键性排序：

| 级别 | 要求 | 为什么 |
|---|---|---|
| **P0** | **对中式口音英语的 ASR 准确率** | 转录错 → 命中错 → 炼化错 → 整条价值链塌 |
| **P0** | 转录文本的**一等公民访问权** | 命中、炼化、回顾直接吃它；还要能独立测 WER |
| **P1** | AI 回复**可控**（短、可比 i+1、能示范目标表达） | 练习场景 AI 是陪练+示范，不是聊天对手 |
| **P1** | AI **有声音** | 口语 App 的哑巴 AI 直接击穿产品前提 |
| **P2** | 亚秒延迟 / barge-in | 用户每轮说 5–60 秒；练习不是抢话 |

**注意 P0 的第二条会直接决定架构选型。**

## 2. 结构判断：端到端 duplex vs 分解流水线

现状用 **Seeduplex（端到端全双工）**：一个模型同时做 ASR + 对话生成 + TTS。它是为"实时语音助手"设计的原语。

**我的判断：它与本产品的核心机制错配**，五条结构性理由：

1. **P0 交给了别人且拿不回来。** 转录是 duplex 会话的**副产品**而非契约 —— 不能独立测 WER、不能换 ASR、不能对转录做二次处理。而 WER 恰恰是最该盯的指标。
2. **无法确定性控制 AI 说什么。** 命中之后要让 AI 在下一句用上更地道的表达 —— 但 duplex 只能靠 system prompt「建议」。
3. **回复长度/难度不可控。** 练习最怕 AI 长篇大论压缩用户说话时间。流水线里这是 `max_tokens` + 校验；duplex 里只能祈祷 prompt。
4. **成本与可观测性都是黑盒。** ASR / LLM / TTS 三段成本混在一个单价里，无法归因、无法熔断、无法 A/B。
5. **端到端最擅长的你恰恰不需要。** 它优化抢话、打断、语气停顿；而本产品**把 barge-in 降级成了手动按钮**。

分解流水线（流式 ASR → LLM → 流式 TTS）给的正是最缺的：转录一等、ASR 可测可换、LLM 输出可校验、TTS 音色可指定、每段可单独计费与熔断。

## 3. 官方事实交叉核对

### 3.1 ⚠️ 先修正我自己的一个错误假设

**我原以为"用官方 SDK 能换来重连与弱网对抗"。查完官方文档：不能。**

我 grep 过官方全双工 iOS SDK 文档全文，**「重连」「断线」命中 0 次**；SDK 文档里**没有**自动重连、会话恢复、弱网对抗、超时重试、音频路由管理这些章节。

**官方 SDK 真正独有、裸 WebSocket 拿不到的，只有这些**（全部有官方原文依据）：

| 能力 | 依据 |
|---|---|
| **AEC 回声消除**（含 `aec.model` 模型文件） | 「Dialog SDK 内置 AEC 能力」（需开启 + 配置模型路径） |
| 录音/播放生命周期管理 | `SE_RECORDER_TYPE_*`、`SE_PARAMS_KEY_DIALOG_ENABLE_PLAYER_BOOL`、可落盘 `.wav` |
| 内部重采样 | `SE_PARAMS_KEY_ENABLE_RESAMPLER_BOOL` + 自定义采样率/通道 |
| 解码后原始音频回调 / 播放进度回调 | `..._ENABLE_DECODER_AUDIO_CALLBACK_BOOL` / `..._PLAYER_AUDIO_CALLBACK_BOOL` |

→ **结论修正**：SDK 的价值集中在 **AEC + 音频管线**，**不在可靠性**。原来"自建要自己负责重连"的说法仍然成立，但**换 SDK 并不会免除它**。

### 3.2 官方硬性约束（这几条改变结论）

**① 音频必须以 20ms 为单位、按实时节奏发送 —— 这是硬要求，不是建议。**

> 官方原文：「音频分片建议以 20ms 为单位（16k/int16 格式下每包 640 字节），并**严格按照实时音频流的节奏发送**，发送速率偏离实际节奏（过快或过慢）都将**触发服务端错误**」

**这直接回答了"60 秒音频一帧发上去会怎样"**：不只是会撞我们自己的 32 KiB 读上限（那个已修，见 `fluentwork-backend/docs/48`）—— **它在供应商侧根本不是一种被支持的用法**。

> 推论：客户端必须**持续、实时、按节奏**地喂音频。这解释了网关里 `sendSilence` 每 20ms 写一次的设计。

**② 麦克风停下必须显式发静音/取消静音事件。**

> 官方原文：「模型依赖上行音频流保活。客户端关闭麦克风后若不再发送音频帧，须主动发送静音事件 `input_audio_mute.commit`，恢复麦克风时发送取消静音事件 `input_audio_unmute.commit`，**否则服务端会因持续收不到音频输入触发超时，导致模型无响应**」

**🔴 这是一条对当前实现的风险提示。** 我们刚做完的 `docs/40`（iOS 停止轮次外 PCM 上行）让客户端在**两轮之间完全不发音频**。按官方这条，那正好是"关闭麦克风"的场景 —— **应当补发 `input_audio_mute.commit`**，否则可能触发服务端超时。

真机实测（修复后 4 轮全部 `outcome=ok`）说明暂时没炸，但**这是"没炸"而不是"正确"**，建议纳入真机回归项。

**③ 协议形态正好对得上。** 官方 3.0 是「纯 JSON 文本帧 + Base64 内嵌音频」。我们网关发的就是 `{"type":"input_audio_buffer.append","audio":"<base64>"}` —— **同一条协议，无迁移成本**。

**④ 输入输出格式**：输入 `pcm`/`speech_opus` **仅 16kHz**；输出 `pcm`/`ogg_opus` **仅 24kHz**。与实现一致。

### 3.3 AEC：一个还没有机会暴露的风险

| 方案 | AEC 来源 |
|---|---|
| 官方 Dialog SDK | **SDK 内置**（需开启 + 模型文件） |
| 裸 WebSocket | **无**。协议文档里没有任何 AEC 字段 |
| 阿里云百炼 Lite SDK | 官方原文明确「**不提供此算法模块**」 |
| Apple | `.playAndRecord` + **`.voiceChat`** 才启用系统 Voice-Processing（AEC + 降噪 + AGC）；只写 `.playAndRecord` **没有回声消除** |

**当前状态：AI 根本没有声音，所以 AEC 从未被真正考验过。**

**一旦让 AI 出声，AEC 立刻变成关键路径** —— 否则 AI 会听到自己的声音，触发自激或误判 barge-in。而这条**恰恰是裸 WebSocket 方案不给的**，必须依赖 Apple 的 `.voiceChat`（实现里确实是 `.playAndRecord` + `.voiceChat`，方向对，但**从未在"有 AI 声音"的条件下验证过**）。

→ **建议：把"AEC 验证"作为"让 AI 出声"的同一个动作，不要拆成两步。**

### 3.4 成本测算（估算，须以控制台账单为准）

官方价目（原文表格）：

| 项 | 单价 |
|---|---|
| 端到端实时语音 · 输入音频 | 80 元/百万 token，**1 秒 ≈ 6.25 token** |
| 端到端实时语音 · 输出音频 | 300 元/百万 token，**1 秒 ≈ 25 token** |
| 豆包流式语音识别 2.0 | **1 元/小时**（并发版 500 元/并发/月） |
| Seed TTS 2.0 | **3 元/万字符**（预付费阶梯最低 2.1 元/万字符）；音色槽位 **138 元/音色** |

**换算成"练习 1 小时"（假设用户说话 0.5h、AI 说话 0.3h）：**

| 方案 | 拆解 | 合计 |
|---|---|---|
| **端到端 duplex** | 输入音频 6.25×1800s×80/1e6 = 0.90 元<br>输出音频 25×1080s×300/1e6 = **8.10 元**<br>文本 token ≈ 0.2 元 | **≈ 9.2 元/小时** |
| **分解流水线** | ASR 1×0.5h = 0.50 元<br>TTS ~5400 字符 × 3 元/万 = 1.62 元<br>Ark LLM ≈ 0.5 元 | **≈ 2.6 元/小时** |

→ **分解流水线约便宜 3.5 倍**，差距主要来自 **duplex 的输出音频按 token 计费（0.45 元/分钟 AI 语音）**。

> ⚠️ **两个必须说明的不确定性**：
> 1. 官方计费文档**自身矛盾** —— 表格写"输出-文本 80 元/百万 token"，但官方计费示例里按 30 元/百万算，差 2.67 倍。**必须以控制台实际账单为准。**
> 2. 上面的说话时长占比是假设，不是实测。**当前系统没有语音成本记账**（见 `53_` §2.3），所以拿不到真实占比。

**另一条硬事实**：端到端实时语音**不支持预付费资源包**（官方表格标"不支持"），仅后付费、小时结 —— 对成本可预测性不利；而 ASR / TTS 都有阶梯预付费。

### 3.5 顺带核实到的两件事

- **官方全双工 iOS SDK 存在，而且指向的就是我们在用的那个端点**（`wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue`，`SEProtocolTypeSeedDuplex`）。所以"没有官方 SDK 只能自研"是不成立的 —— 是**选择**自研，不是**被迫**。
- **模型版本号存疑**：我们配置用 `1.2.6.0`，官方全双工 API 文档写**固定值 `1.2.6.1`**，公开资料查不到 `1.2.6.0`。真机日志显示 `1.2.6.0` 能用，但**建议回控制台核对**，这可能是服务端升版留下的兼容口径。

## 4. 结论与建议

### 4.1 我对"用不用 SDK"的立场：**分层，不是一刀切**

| 层 | 选择 | 理由 |
|---|---|---|
| **服务端调 ASR / LLM / TTS** | **裸协议** | 你要可观测、可替换、可单独计费；官方服务端 SDK 会把这些包进黑盒并锁定供应商 |
| **iOS 播放 TTS 音频** | **值得用 SDK（或现成解码方案）** | 这是 SDK 唯一真正值钱的地方：解码、jitter buffer、播放中断、音频路由 |
| **iOS 采集** | **自研（现状即可）** | `AVAudioEngine` + 重采样是标准做法；用 SDK 反而拿不到原始 PCM 做质检 |
| **iOS 持有凭证** | **坚决不** | 现状正确，且罕见地克制 |
| **AEC** | **必须明确来源** | 裸 WS 不给；只能靠 Apple `.voiceChat`。**这是分层方案里最薄的一环，要单独验** |

**一句话：SDK 用在"媒体处理的脏活"上，不用在"协议与业务"上。**

### 4.2 结构上，我建议的方向

**中期：从端到端 duplex 迁向分解流水线（流式 ASR → Ark → 流式 TTS）。** 判据是 §2 那五条 + §3.4 的成本差。

**但现在不要动。** 理由：**基线不存在**。当前连"AI 出声"都没有，此时换架构等于同时改两个变量，之后的问题分不清来源。

### 4.3 建议的动手顺序

| # | 动作 | 为什么是现在 |
|---|---|---|
| **1** | **让 AI 先出声** —— 走最短路径：网关把厂商已经推下来的 `response.output_audio.delta` 转给 iOS | 零新增供应商、零新增成本，当天可听到声音。**但见 §4.4 的两个坑** |
| **2** | **同一动作里验 AEC** | 出声之后 AEC 才是活的；分开做会重复劳动 |
| **3** | **给语音链路加成本记账** | 不做就永远拿不到 §3.4 里的真实占比，也就无法判断该不该迁 |
| **4** | **拿 30 条中式口音英语样本测 ASR 的 WER** | 这是 P0 指标。**拆不拆流水线，应该由这个数字决定，不由理念决定** |
| **5** | 补 `input_audio_mute.commit`（见 §3.2②） | 消除一个已知的"没炸但不正确" |

### 4.4 「让 AI 先出声」这一步的两个坑（必须一起处理）

**坑一：当前不是真流式。** `turnToOutbound` 把**整轮累积后**的文本一次性发出；`collectTurn` 读完整轮才返回。所以即使转发了音频，也会**堆在轮末一次性到达** —— 用户听到的是"AI 沉默两秒，然后一口气说完"。要真有流式感，`collectTurn` 必须能边读边发。

**坑二：音色不可控。** duplex 内置 TTS 的音色/语速/语言由模型决定。先出声可以接受，但**要作为一次性验证**，不要当成产品终态。

## 5. 与既有结论的对照（仅作对照，非论据）

| 既有结论 | 出处 | 本文的核对结果 |
|---|---|---|
| 不接官方客户端 SDK，全链路自研 relay | `71_`/`72_`/`73_`/`62_` | **方向认同**，但理由要更新：不是因为 SDK 没有价值，而是价值集中在 AEC/媒体层，而**可靠性 SDK 也不给**（§3.1） |
| 不引入 seed-tts-2.0 iOS SDK | `73_` | 与本文 §4.1 一致（服务端裸协议）。但 `73_` 的结论建立在"SDK 是否支持自定义 WSS endpoint 未确认"之上；**本次调研确认 TTS SDK 走的是独立端点 `wss://.../api/v3/tts/bidirection`**，与混合模式的前提不同 |
| 结论"需要 PoC，而不是文档猜测" | `72_` | **认同**。本文 §3.4 的成本与 §3.2② 的保活要求，都必须实测确认 |

**唯一实质分歧**：既有结论把"不接 SDK"的代价描述得偏轻。本文认为**那层代价是真实且已经付过一次的**（`52_` 里的两个读上限、reopen 预算、每轮失忆，全部出自这一层）。

## 6. 需要实测确认的（不要用文档猜）

1. **成本**：`1 小时练习`的真实 token/字符数（依赖 §4.3 第 3 项）
2. **AEC**：`.voiceChat` 在"AI 出声 + 外放"下是否足够；不足则需评估 SDK 的 AEC 模块
3. **ASR WER**：30 条中式口音英语样本
4. **模型版本**：控制台核对 `1.2.6.0` vs 官方文档的 `1.2.6.1`
5. **保活**：不发 `input_audio_mute.commit` 时服务端的实际超时行为
