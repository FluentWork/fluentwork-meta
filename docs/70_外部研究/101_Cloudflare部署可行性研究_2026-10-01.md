# Cloudflare 部署可行性研究

> 文档版本：v1.0
> 创建日期：2026-10-01
> 目标读者：架构决策人、backend 负责人
> 结论性质：**可行性评估（不做实施）**
> 证据基础：`fluentwork-backend` 现仓源码实读 + Cloudflare 官方文档（2026-10 时点）

---

## 一、结论先行

**技术上可行，但不推荐在当前形态下部署。**

Cloudflare 在 2026-04 将 Containers 正式 GA，这就把"Go 编译产物跑不跑得起来"这个问题解掉了——你的三个服务都能以容器形态跑上去。但真正卡住这条路的是三条与代码无关的约束：

| # | 约束 | 性质 | 影响的组件 |
|---|---|---|---|
| 1 | **Cloudflare 中国区（China Network）不提供 Containers / Durable Objects** | 硬阻断 | 全部服务（面向大陆用户时） |
| 2 | **Cloudflare 没有托管 MySQL**，Hyperdrive 只是连接池，不托管数据 | 硬阻断 | app-server / worker |
| 3 | **语音双工链路对出境延迟极敏感**，而 cloudflare 调度不可锁区域 | 高风险 | voice-gateway |

其中第 1 条是决定性的：**你的语音链路要生成好的体验，就必须离 `openspeech.bytedance.com` 近；而 Cloudflare 能跑容器的节点全在境外。** 这两件事无法同时成立。

## 二、现状盘点（实读，非推测）

### 2.1 三个服务

| 二进制 | 入口 | 端口 | 关键依赖 |
|---|---|---|---|
| `app-server` | `cmd/app-server` | 8080 | Gin、MySQL、JWT；对外发 `wss_url` 给客户端 |
| `voice-gateway` | `cmd/voice-gateway` | 8081 | 入站 WSS（客户端）、**出站 WSS 到火山引擎**、内部 HTTP 调 app-server |
| `worker` | `cmd/worker` | — | MySQL outbox 轮询（`session_jobs`）、Ark LLM 调用 |

### 2.2 语音链路的真实形态（决定性的那一段）

`internal/voiceduplex/volc_duplex.go:44`：

```go
DefaultDuplexEndpoint = "wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue"
```

这条 **出站 WebSocket 是长连接的、双工的、对延迟敏感的**。语音网关不是"收完再转发"的普通 API，而是实时中继：客户端 PCM 上行 → 火山 Seeduplex 双工 API → TTS 音频下行 → 客户端播放。打断（`handler_control.go`）、静音检测（`silence_detector.go`）、轮次归属（`turn.go`）全都建立在低 RTT 假设上。

### 2.3 Redis：**代码里根本没实装**

这一点值得单独指出，因为现有文档把它写成了硬依赖：

- `SETUP.md:7` 写 "Redis 7.0+"
- `deploy/docker-compose.yml:21` 起了一个 `redis:7`
- `scripts/dev-status.sh:51` 会探测 6379 端口

但**全仓 Go 生产代码对 Redis 的引用数为 0**。唯一的痕迹是 `migrations/0005_create_session_jobs.sql` 的一句注释：

```sql
-- Async session.finished outbox for B5 review worker (Redis Stream can replace later).
```

即 Redis 是"预留但未启用"。**部署选型的真实依赖面只有 MySQL 一个。** 这反而是个好消息——如果将来换云，Redis 这一项迁移成本为零。

### 2.4 容器化就绪度

`Dockerfile` 已经是：

```
CGO_ENABLED=0 GOOS=linux go build   →   distroless/static-debian12:nonroot
```

静态链接、无 CGO、linux/amd64。这与 Containers 的要求（linux/amd64 镜像）**天然吻合**，这一层零改造。

### 2.5 依赖的外部服务

全部是境内的火山引擎资产（`ARK_BASE_URL`、`ARK_EP_*` 六个推理端点、`VOLC_SPEECH_*`、`VOLC_DUPLEX_*`）。**没有一个依赖在境外。** 这意味着把计算搬出境，等于给每一条 LLM / 语音调用都加一段跨境往返。

## 三、能力映射：你需要什么 vs Cloudflare 给什么

| 你的需求 | Cloudflare 对应能力 | 判断 |
|---|---|---|
| 跑 Gin/Go HTTP 服务 | **Workers 不行**（只有 JS/WASM 与 TinyGo，无 `net/http`、无 socket）；**Containers 可以** | ⚠️ 只能走 Containers |
| 跑长连接 WSS 语音网关 | Containers WebSocket 转发（`container.fetch` + DO）+ Durable Objects | ⚠️ 可做，但有下面第四节的问题 |
| 托管 MySQL 8 | **无**。D1 是 SQLite（10 GB/库上限），不是 MySQL | ❌ 数据必须留在外部 |
| 加速 Worker→MySQL 连接 | Hyperdrive（2026-08 MySQL GA） | ✅ 只是连接池，不迁移数据 |
| Redis / 缓存 | 无托管 Redis。可选 Upstash（外部）、DO、KV | ➖ 你当前没用到 |
| 异步任务队列 | Queues + Cron Triggers + Workflows | ✅ 但你用 MySQL outbox，本来也不需要 |
| 对象存储 | R2 | ✅ 无 egress 费 |
| 定时任务 | Cron Triggers | ✅ |
| 中国大陆节点 | China Network（京东云运营） | ❌ 见第四节，**不含 Containers/DO** |
| 容器之间私有网络 | **无**。容器只能经 Worker/DO 访问 | ❌ 影响内部信任边界 |

## 四、四条关键风险，逐条展开

### 4.1 中国区不提供 Containers —— 硬阻断

Cloudflare 官方 `Available products and features`（China Network，京东云运营）列出的开发者服务只有：

> Workers、Workers KV、R2、Assets、Images、mTLS、Rate Limiting、Secrets、Service bindings、Tail Workers、Workers for Platforms

**没有 Containers，没有 Durable Objects，没有 D1，没有 Hyperdrive，没有 Queues。** 而且列表里 Workers 的注释是 "running on the Cloudflare **global** network"——即便这一项，执行位置也不在大陆。

同时入场门槛是：**Enterprise 套餐 + 每个 apex 域名独立 ICP 备案 + 京东云内容审核**，且中国大陆内容受属地监管。

**推论：** 想让大陆用户的语音链路走 Cloudflare 大陆节点 —— 做不到。Containers 只能落在香港/新加坡/东京/首尔/洛杉矶等境外节点。对国内用户来说，这既是延迟问题，也是数据出境问题（PIPL：语音是个人信息，跨境需评估或标准合同）。

### 4.2 Containers 的调度不可控 —— 语音延迟的最大不确定性

Containers 的放置逻辑是"离发起请求的用户最近的**空闲**实例"，开发者只能给 Durable Object 一个 `locationHint`（`apac` / `wnam` / …），**不能钉到具体城市或区域**。而 `apac` 覆盖范围极广。

后果：一个上海用户的语音会话，网关可能落在新加坡，也可能落在东京，甚至在高负载时被调度到更远的位置。**你的双工链路延迟预算会变成一个不可预测的变量**——而打断、静音检测这些逻辑恰恰建立在确定性的 RTT 上。

参考量级（到 `openspeech.bytedance.com`，中国大陆）：香港 ~30–50 ms，新加坡 ~60–80 ms，东京 ~60 ms，美西 ~180 ms+。双工语音的"耳到嘴"体感预算通常在 150 ms 量级，扣掉 ASR/TTS 自身耗时后，留给跨境传输的空间非常有限。

同理，`worker` 里的 6 个 Ark 推理端点（`ark-endpoint-probe`、`smoke-ark-go-ping` 就是为压测这些端点存在的）每一次调用也会跨境。你现有的 `defaultArkHTTPTimeout = 30 * time.Second` 是**实测标定**出来的（`config.go` 注释提到"标定最大值加余量"），出境后这个值大概率不够。

### 4.3 长连接在这个平台上要重写的三件事

**(a) 100 秒静默断开。** Cloudflare 对经其边缘代理的 WebSocket 有 ~100 s 空闲超时，Free/Pro/Business 固定不可调（Enterprise 可配置）。你的语音链路有 `silence_detector.go`——**说明静默是真实存在的状态**。用户中途停顿超过 100 s，连接会被边缘静默掐断。需要加服务端心跳（30–60 s ping），而这条心跳现在没有。

**(b) DO 带着出站 WSS 时无法休眠。** 官方生命周期文档明确列出休眠前提之一是"不存在活跃的出站 TCP socket 或出站 WebSocket 连接"。语音网关到火山的那条 WSS 一开，**DO 就永远醒着**，按整段会话时长计费，且无法靠 hibernation 省钱。

**(c) 每次部署会掐断所有在线会话。** 官方文档："Code updates will disconnect all WebSockets. If you deploy a new version of a Worker, every Durable Object is restarted." 你已有 `speech_reconnect_started` 埋点和 rescue 阶梯（`rescue_orchestrator.go`），**部分**能兜住，但一个 10 分钟的语音会话因一次部署中断，用户体验是实打实的损伤。Containers 还有一条额外的坑：滚动更新期间 **新 Worker 代码必须向后兼容旧容器代码**。

### 4.4 容器之间没有私有网络 —— 内部信任边界要重做

当前 `voice-gateway` 通过内网 HTTP 调 `app-server`：

```
POST /internal/v1/tickets/consume      （凭 InternalAPIToken 互信）
```

在 Cloudflare 上，容器没有内网地址，**不能直接互相访问**——只能 `Worker → Durable Object → Container`。所以这条内部调用要么绕经 Worker（多一跳、要重构鉴权），要么走公网。原本靠"不可从公网到达"成立的 `InternalAPIToken` 安全假设，**在 Cloudflare 上不再成立，必须重新设计**。

## 五、成本测算

计费口径（Workers Paid $5/月，含 25 GiB-h 内存、375 vCPU-min、200 GB-h 磁盘）：

- 内存 `$0.0000025 / GiB-s`，CPU `$0.000020 / vCPU-s`，磁盘 `$0.00000007 / GB-s`
- **关键**：CPU 按实际用量计，**内存与磁盘按挂载容量 × 醒着的墙钟时间计**，与负载无关

### 场景 A — 每会话一个语音容器（standard-1：0.5 vCPU / 4 GiB / 8 GB）

一次 30 分钟会话（1800 s），CPU 按 20% 利用率估：

| 项 | 计算 | 成本 |
|---|---|---|
| 内存 | 4 GiB × 1800 s × $0.0000025 | $0.0180 |
| 磁盘 | 8 GB × 1800 s × $0.00000007 | $0.0010 |
| CPU | 0.1 vCPU × 1800 s × $0.000020 | $0.0036 |
| **合计** | | **≈ $0.023 / 会话** |

1000 场会话/月 ≈ **$23**。这一项其实相当便宜——**因为语音是突发负载，scale-to-zero 是划算的**。

### 场景 B — 常驻容器（worker 或避免冷启动的网关）

standard-1 保持 24/7 醒着（730 h）：

| 项 | 计算 | 成本 |
|---|---|---|
| 内存 | (4 × 730 − 25) GiB-h | $26.06 |
| 磁盘 | (8 × 730 − 200) GB-h | $1.42 |
| CPU | 按 5% 利用率 | $0.86 |
| Workers Paid 底费 | | $5.00 |
| **合计** | | **≈ $33 / 月** |

**注意这个"地板"：即便容器什么都不干，内存+磁盘两项也要 $27.5/月。** 常驻型服务在 Containers 上不存在"便宜"的可能。

### 场景 C — Durable Object 开销

每个容器绑定一个 DO，按 `$12.50 / 百万 GB-s` 计。一个 128 MB 的 DO 常驻 24/7：

```
0.125 GiB × 2,628,000 s = 328,500 GB-s → $4.11 / 月
```

再加请求费 `$0.15/百万`。

### 汇总

| 组件 | 形态 | 估算 |
|---|---|---|
| app-server | 突发，scale-to-zero | 大概率在 $5 底费的含额度内 |
| worker | 常驻（轮询 outbox） | ~$33/月 |
| voice-gateway | 每会话 | ~$0.023/会话 |
| DO | 每个容器一个 | $4–10/月 |
| MySQL | **外部**，另计 | — |
| **合计** | | **约 $60–120/月** |

对照组：同规格 VPS（2 vCPU / 4 GiB）约 **$6–12/月**，云厂商 ECS 同档位接近。**在当前阶段，Cloudflare Containers 的价格结构对"常驻服务"是不划算的**，它的设计意图就是给突发型、能睡的负载用的。

## 六、如果仍要在 Cloudflare 上做，最小可行形态

**务实的分层方案（推荐度：中）**

| 层 | 放哪 | 理由 |
|---|---|---|
| app-server | Cloudflare Containers + 外部 MySQL + Hyperdrive | 无状态、突发型、与边缘亲和；这是 Containers 的理想负载 |
| MySQL | 火山/阿里云 RDS（境外或境内取决于用户分布） | Cloudflare 不托管，必须自备 |
| voice-gateway | **留在国内**（火山 ECS） | 贴近 `openspeech.bytedance.com`，规避出境与不可控调度 |
| worker | 国内 | 6 个 Ark 端点全在境内，出境纯亏 |

这个形态能成立，但它已经**不是"把后端部署到 Cloudflare"**，而是"把其中一个无状态服务放上去"。收益（边缘加速、免运维）与代价（多一套部署链路、多一个故障面、跨云网络）在早期并不划算。

**不推荐的形态**：三个服务全上 Cloudflare。三条硬约束会同时兑现。

**需要等待的**：China Network 支持 Containers/DO（目前**无时间表**，且不在官方 available list 上）。

## 七、替代方向

| 用户分布 | 建议 | 说明 |
|---|---|---|
| 主要在中国大陆 | 火山引擎 / 阿里云 / 腾讯云 | 贴近日均调用链、无出境合规问题、成本可预测 |
| 主要在海外 | Cloudflare 是**优秀**选择 | 此时三条约束全部消失：无 ICP 问题、延迟目标变化、MySQL 可换 Postgres/D1 |
| 混合 | 前端/静态资产走 Cloudflare CDN，后端分区域部署 | 常见做法 |

你的语音链路、LLM 端点、产品文档全部指向大陆用户。在这个前提下，**Cloudflare 更适合承担边缘 CDN 与安全层（WAF/DDoS），而不是计算层。**
