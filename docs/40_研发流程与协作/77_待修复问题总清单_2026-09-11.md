## 0. 前提:方案已定

**继续自研 relay,不引入官方客户端语音 SDK。**

**同时:传输层不引入第三方 WebSocket 框架**（继续用 `URLSessionWebSocketTask`）。依据、义务与推翻条件见 [`54_传输层不引入第三方WebSocket框架`](../30_技术方案/54_传输层不引入第三方WebSocket框架_2026-09-11.md)。

这不是"因为厂商没有 SDK"—— `74_` 已核实:火山的全双工 iOS SDK 存在,而且指向的就是我们在用的那个端点。是**选择**自研,不是**被迫**。

理由(按重要性)：客户端零凭证是硬约束；转录/事件/置信度必须留在服务端一手可见；官方 SDK 的价值集中在 **AEC + 音频管线**,而**可靠性它也不给**(其文档无重连/恢复/重试章节)。

**分层立场**(`74_` §4.1)：服务端调 ASR/LLM/TTS 用裸协议；iOS 播放音频可以用现成解码方案；采集自研；**AEC 必须明确来源**。

#### P1-7 备注：播放门禁水位线的生命周期（保留上下文）

**客户端有 2 道水位线，彼此独立，且都只在会话级重置：**

| 门禁 | 位置 | 置位 | 清除 |
|---|---|---|---|
| `AudioPlaybackGate.interruptWatermark` | `LiveAudioEngine` | `interruptNow()` | `startCapture()` / `stopCapture()` |
| `AudioFrameDropGate.interruptMaxSequence` | `URLSessionSocketTransport` | `transport.markInterrupted()` | **只有 `connect()`** |

第二道的 `clearInterrupt()` **在生产代码里零调用**（只有定义和测试）—— 设下后整个连接期间永不清除。

**2026-09-11 实测复发**：真机「播放不全，有时前半段、有时后半段」。成因是第二道门禁 + 当时尚未部署的 F18：barge-in 设下水位线 W → 网关重开把序号从 1 重来 → 传输层把新一轮的 1..W 全丢在到达引擎之前。**不需要滚动**，触发条件是重开。

**现状**（`fluentwork-ios` `LiveAudioEngine`）：

```swift
struct AudioPlaybackGate {
    private(set) var interruptWatermark: UInt32?    // 由 interruptNow() 设下
    mutating func shouldAccept(_ frame: WSAudioFrame) -> Bool {
        if let interruptWatermark, frame.sequence <= interruptWatermark { return false }
        ...
    }
}
```

它**只在 `startCapture()` / `stopCapture()` 重置** —— 即整场会话级别，从不按轮清理。

**它要解决的问题是单轮的**：打断（barge-in / 系统中断）发生时，把**那一轮**已经排进播放队列的在途音频丢掉。这个目的是**轮次范围**的，而实现给了它**会话范围**的生命周期。这个错配就是全部风险来源。

**已修的部分**（F18）：后端透明重开曾把序号从 1 重来，撞上停在几百的水位线 → 之后每一帧被**静默**丢弃。表现是「文字照常返回、音频永久消失、不报错」。后端已改为跨重开接力编号。

**残留**：水位线的生命周期仍然错配。将来任何别的序号回退路径（新的重开路径、新的 provider、协议改动）都会以**完全相同**的方式复发 —— 而且是静默的。

**修法方向**：让水位线**按轮失效**。打断那一轮真正结束时清掉它。需要一个可靠的轮次边界信号，`ai.turn.end`（带 `turn_id`）是现成的候选，但它目前没有喂给播放门禁这条路径。

**明确否决的做法**：客户端加「序号看起来变小了就重置」的启发式。门禁逻辑本身没错，错的是它依赖的前提；启发式会在**真正的乱序场景**下帮倒忙，而且会把真 bug 藏起来。

**已做（可观测）**：`docs/46` 让两道门禁的丢弃都留下记录 —— `SocketTransportDiagnostic.audioFrameDropped` + tracker 事件 `transport_audio_dropped`，报告规则抽成 `AudioDropReport` 纯类型。`sequence <= watermark` 却出现在设下水位线那一轮之后，就是序号回退的签名。判据从"猜"变成"读"。

### ~~P1-9~~ ✅ — 测试基础设施：`.singleton` 工厂的注册会跨测试泄漏

**已实测踩到**：`processingTimeouts` 是 `.singleton`，一个测试注册 80ms `connectWait` 后，`transitionTelemetryEmittedOnPhaseChange` 与 `ttsStreamEmitsStartFirstAudioAndEndViaSharedTracker` **5 次里挂 3 次**，单独跑却 4/4 全过。

**机制**：`.singleton` 让注册变成**进程级**粘性 —— 注入的值泄漏给所有**并发**运行的测试。测试里 `defer` 还原只在测试结束后生效，救不了同时跑的；两个受害者在另一个 suite，所以 `.serialized` 也救不了。

**已修**：`processingTimeouts` 去掉 `.singleton`（无状态值类型，缓存本就没有意义）。5/5 全绿。

**同类风险仍在** —— 另有 4 个 `.singleton` 工厂被测试 `register`：

| 工厂 | 泄漏症状 |
|---|---|
| `corpusCacheStore` | 别的测试拿到你这个假 cache |
| `corpusOutboxStore` | 同上 |
| `corpusSyncMetadataStore` | 同上 |
| `networkMonitor` | 别的测试拿到你写死的网络状态 |

机制与 `processingTimeouts` 完全相同，只是注入的是**有状态替身**而非纯数值，所以症状是「拿到别人的假对象」而不是「时序被静默改变」。**还没撞出可见失败，但风险是同一类。**

**已修**（ios `4821184` + `ios docs/56`）。**缓存作用域语义已确认，且比本行的措辞更彻底**：`Scope.Singleton` 的注释是字面的 —— *"ignore container's cache in favor of our own"* —— 它用的是**自己的**缓存，而 `self` 是共享的 `Scope.singleton`。所以 `Container()` 是不是新的无关紧要、`container.reset()` 清不掉、`defer` 更没用。**不是"单例缓存破坏隔离"，是单例作用域根本不在容器里。** 所以有状态替身不需要额外的隔离机制，它需要的是**换一个作用域**。

修法：`.singleton` → `.cached`（`Cached` 不覆写 `resolve`，用的是传进来的容器缓存，且 `reset()` 会清掉它）。**范围是全部 25 处，不只是本行点名的四个** —— 因为生产代码永远走 `Container.shared`：`AppStore` 与四个 Middleware 工厂的签名都是 `container: Container? = nil` → `container ?? Container.shared`，而**生产调用点一个都没传**。那个参数存在的唯一目的就是让测试注入新容器，而 `.singleton` 恰好废掉了这个注入。**这不是宽改动，是让 DI 的设计意图成立。**

守卫写成**性质**（两个独立容器不共享实例）而不是点名，将来新加的工厂若也用 `.singleton` 照样抓得住。**顺带撞出一个编译器 bug**：`(existential as AnyObject) !== (existential as AnyObject)` 让 Swift 6.3.3 直接崩（signal 6，不是类型错误），需先转型到具体类型 —— 看起来像自己的代码写错了，实为工具链问题，已记档。`swift test` 458/458 |

### ~~P1-11~~ ✅ — 读错误分类过宽：`context.Canceled` 被当成"上游连接已死"

`voicepoc.collectTurn` 的读错误只区分 `context.DeadlineExceeded`，**其余全部**包成 `ErrDuplexClosed`：

```go
if errors.Is(err, context.DeadlineExceeded) { /* 优雅降级 */ }
else { collectErr = fmt.Errorf("%w: %w", ErrDuplexClosed, err) }   // ← context.Canceled 也走这里
```

而 provider 拿到 `ErrDuplexClosed` 就 **reset 整个 duplex**，丢弃服务端会话上下文。

**为什么算缺陷**：同一份代码在另一处的注释里明确写着立场 ——「provider error 事件不同于连接死亡，reset 会丢弃服务端上下文」。分类把**调用方主动取消**和**套接字真的死了**混成一类，与那个立场不一致。

**影响面**：生产上 `HandleClientControl` 拿到的是 WSS handler 的 ctx，客户端断开时取消 —— 那种情况下 reset 无害（会话本来就要结束）。所以**不是紧急缺陷**，但它让"哪些情况该 reset"这个问题失去了精确答案。

**已修**（backend `da60576` + `docs/57`）。新增 sentinel `ErrTurnCancelled`，把取消从"断连"里摘出来 —— `ErrDuplexClosed` 的语义因此**变纯**：只表示"套接字死了"，正是 `resetAfterTurnReadFailure` 该被调用的那一种；调用方 `errors.Is(err, voicepoc.ErrDuplexClosed)` **一个字没改**就自动不再对取消重置。

**为什么算缺陷（比本行的措辞更准）**：就在那个 `if` 上方三行，注释写着 *"A provider error event is different: the session is still usable and resetting would discard the server-side conversation context"* —— 这份代码**已经**在按"会话还能不能用"分类，而且明确把"重置会丢弃服务端上下文"当成代价，却又让 `Canceled` 走进重置分支。**分类粒度与它自己的立场对不上**，而不只是"分类过宽"。

红验证抓出的实际输出：`canceled` 被逐字包成 `duplex connection closed: failed to get reader: context canceled` |

**发现于**：步 6 排查时（写测试时用了短 ctx，撞出了这个分类）。

## 3. AEC 怎么做

**先说结论:主方案是 Apple 的 Voice-Processing I/O,而它现在很可能没真正生效。**

### 3.1 三条可选路径

| 路径 | 做法 | 代价 |
|---|---|---|
| **① Apple Voice-Processing I/O(主)** | 系统级 AEC + 降噪 + AGC,免费、无包体、不引第三方 | 需要正确启用 + 实测;有已知的格式副作用 |
| **② 半双工兜底** | AI 播放时**停止上行麦克风** | 简单、必定有效。但**牺牲 barge-in**(用户不能打断 AI) |
| **③ 官方 SDK 的 AEC** | SDK 内置,需配 `aec.model` 模型文件 | **与本仓自研 + 零 key 约束冲突**,只在 ① 实测不行时评估 |

### 3.2 ① 为什么可能没生效 —— 两套 API 要分清

| API | 现状 | 说明 |
|---|---|---|
| `AVAudioSession` category `.playAndRecord` + mode **`.voiceChat`** | **已配置** ✅ | 这是**会话级**的 VPIO 开关 |
| `AVAudioEngine.inputNode.**setVoiceProcessingEnabled(true)**` | **未配置** ❌ | 这是**引擎级**的开关(iOS 13+)。用 `AVAudioEngine` 自建图时,这一条往往才是决定性的 |

当前 `DefaultAudioSessionManager` 只做了前者。**这两者不等价** —— 只设 category 而不用引擎级 API,在自建 AVAudioEngine 图里 AEC 未必生效。

**已知副作用(改动前要预料到)**:开启 input node 的语音处理会**改变输入节点的格式**,可能让现有的 tap/`AVAudioConverter` 链失效。所以这一步要和 `convertToPCM16` 的格式断言一起改。

> **落地后补(ios `ecfaf7d` + `ios docs/63`)—— 这段原来只说"格式会变",没说变成什么、不处理会怎样,而那才是下一个人需要的东西:**
>
> 1. **变成多声道。** 实测常见 3/7/9 声道 deinterleaved Float32,其中**只有第 0 声道是人声**,其余是回声计算的元数据。
> 2. **默认映射是静音,不是 downmix。** 多声道 → 单声道的转换器,`channelMap` 默认值是 **`[-1]`**,而 API 定义里负数 = 该输出声道不取任何输入。**所以不处理的后果是上行空的**,不是"声音被污染"。要显式设 `[0]`。
> 3. **`AVAudioConverter(from:to:)` 的返回值此前从不检查** —— 构造失败 = 永久静默采集。这才是"格式断言"的具体形态。
> 4. **顺序是契约**:开启**就是**改变格式的那一步,先读后开读到的是旧格式。两件事必须合成一个操作。
> 5. **只能在引擎停止时开关**,在运行的引擎上切换抛的是 `NSException`(F12–F16 那一类,`do/catch` 看不见)。

### 3.3 怎么**验证** AEC(不能靠"听起来没回声")

**判据是可观测的,不是主观的:**

| 信号 | 说明 |
|---|---|
| **转录里出现 AI 自己刚说过的话** | AEC 失效最直接的证据 —— 麦克风把扬声器放的 AI 语音录进去,被 ASR 转成了用户输入 |
| **未开口却触发新一轮** | AI 的声音被当成用户说话,触发 server VAD |
| **`interrupt` 自触发** | AI 播放中被自己的声音打断 |

**具体做法**:真机上让 AI 说一段**含独特短语**的话,用户**全程不出声**。

- **AEC 生效** → 该轮 transcript 为空 / 无新一轮
- **AEC 失效** → transcript 里出现那个独特短语

这个测试**必须在 P0-1(AI 出声)之后立刻做**,而且可以自动化断言(比对 transcript 与 AI 上一轮文本)。

**判定工具已就位**：`fluentwork-backend/scripts/check-aec.py`（backend `3f5b2be`）。

```bash
# 真机上静默一轮之后
./scripts/check-aec.py /tmp/fluentwork-backend.log
# exit 0 = 无自激证据；1 = 发现自激
```

它逐会话比对 `transcript` 与上一轮 `assistant_text` 的重合率。分词带**中文二元组** —— 这不是优化是必需:本产品大量会话是中文,纯 ASCII 分词会把每条中文转录判成"空"而跳过,恰好跳过这个脚本存在的意义所在的那批会话。

**已在现有日志上跑过**：10 会话、0 自激。但那批会话用户一直在说话,**回答不了 AEC 问题** —— 弱阳性,不是结论。

### 3.4 失败时的退路

若 ① 实测不达标:**先上 ② 半双工**(播放时停上行),把 barge-in 暂时降级为按钮触发 —— 产品上可接受(`docs/41` 已把交互改成"点一次开始"),工程上立刻消除自激风险。**③ 留作最后手段**。

| **回顾页** | 第一屏只放一件事 —— **"你刚才最值钱的一次升级"**:原句(可回听自己的声音)→ 地道版(AI 朗读)→ 一键入库。三层评价/问题清单全部后置。等待用"高光与卡壳波形回放"填充 |
| **闪测** | 答对反馈**即时且轻**;结算页文案不是"成功率 80%",而是"**'降级'这个词,你已经能脱口而出了**" |
| **语料库** | **按"未来的会议"组织,不按标签**:"下周一 Standup 你可能用到的 5 句话" |

**一句话**:把"刻意练习"伪装成"一次顺利的对话";所有"训练感"发生在对话之外。
