## 0. 这份清单怎么读

### 0.1 分级

**分级只按一件事**：不做会怎样。

| 级 | 含义 | 判据 |
|---|---|---|
| **S0** | 不做就继续带着已知风险跑 | 已在真机出过事故，或需要一个只有人能给的决定 |
| **S1** | 不做会在下一次同类缺陷上再花一遍时间 | 结构上「看起来被守住了，实际上没有东西会红」 |
| **S2** | 不做只是让下一个人多读一会儿 | 重复、命名、注释、死代码 |
| **V** | 待核实 —— **不要用文档猜** | 需要一个外部事实（账单 / 厂商 / 真机） |

原先三份来源用的是两套判据：`P0/P1/P2`（能不能让产品闭环成立）与 `S0/S1/S2`（不做会怎样）。
两套**近乎对应**（P0≈S0、P1≈S1、P2≈V），合并时按上表归一。

### 0.2 编号

**编号是稳定 id，不是分级。** 三条来源的编号**一律保留原样、不改写、不复用** ——
因为全仓有 **58 个文件**引用 `P0-x`/`P1-x`/`P2-x`（`P1-2` 被引 48 次、`P0-1` 33 次），
重编号会打断它们。

**唯一一处消歧**：iOS 与 backend 的 `S0-x`/`S1-x`/`S2-x` **编号完全撞车**
（`S1-1` 在 iOS 是「`pcmBuffer` 不变量」，在 backend 是「`materials` 无租约」）。
所以两套 S 号**加仓前缀**：

| 来源 | 编号写法 |
|---|---|
| 产品与缺陷轴（原 77_） | `F1` / `P0-10` / `P1-17` / `P2-4` —— 原样，无前缀（本来就全局唯一） |
| iOS 架构轴（原 iOS `80_/05_`） | **`iOS-S0-1`** / **`iOS-S1-9`** / **`iOS-S2-11`** |
| backend 架构轴（原 backend `104_/05_`） | **`BE-S0-2`** / **`BE-S1-4`** / **`BE-S2-4`** |

**引用时一律带前缀。** 写「见 `S1-9`」是错的 —— 它有两个所指。

### 0.3 用法规则

1. 每修一条，在对应行标 ✅ 并补上提交哈希与实现说明链接。
2. **一次只推进一条**，跨仓串行（后端与 iOS 不同时改）。
3. **新增问题直接进表，不另开文档。** —— 这条在只有一张表时才真的可执行。
4. **状态只在子文件里改，本文 §2 是视图。**
   ⚠️ **两个仓的 `docs/` 已于 2026-09-25 整体删除**（iOS `80c8209`、backend `e2c61f7`），
   连同 `01`–`04` 架构分析、`70_tts_wss_refactor/`、`103_` 与各实现说明。
   所以三个子文件现在是这些条目**唯一的载体**，不再是「收敛件」；
   子文件里指向原 `01`–`04` 的行号引用**已失效**。
5. 表变长不是坏事 —— **变长且没人动才是。**
