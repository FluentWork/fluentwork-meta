# 方向 A：让音频帧带上轮次归属 —— 契约草案

**日期**：2026-09-12
**状态**：**草案，待定后实施。** 前置：`82_`（方向 B 已落地，backend `1ceeb3f`）
**起因**：`77_` **P0-11** —— 打断停不下「还在途」的那一条音频

## 0. 结论先说：**不需要改二进制帧格式**

我此前把方向 A 描述成「在帧头加轮次」，并因此说它「贵」（两仓锁步、版本错配会让音频整个失效）。**查证之后那个描述是错的** —— 客户端**已经有**这个能力，缺的只是把它打开：

`TTSDecoder.swift` 的协议注释自己写着：

> Binary audio messages do not repeat `turn_id`; **`TTSFrameDispatcher` associates each
> `WSAudioFrame` with the active `ai.tts.start`.**

而丢弃机制也在：

```swift
// After barge-in `interrupt()`, leftover binary frames stay consumed
// (not played as PCM) until `ai.tts.end`.
case .draining: return true     // ← 认领但不播放
```

**所以方向 A = 把 `ai.tts.*` 这条路径打开。** 三块积木全都存在：

| 积木 | 在哪 | 状态 |
|---|---|---|
| `turn_id` 随帧走 | `ai.tts.start`（`AITTSStart.TurnID`）| **已定义**，volc-duplex 不发 |
| 二进制帧按「当前 start」归属 | `TTSFrameDispatcher.stream` | **已实现** |
| 打断后认领但不播放 | `.draining` + `interrupt()` | **已实现** |
| 真正出声的解码器 | `MockTTSDecoder` | **缺** —— 它不驱动 `AVAudioEngine` |

`provider_volc_duplex.go:808` 起那段注释说的正是最后一行：*「绑进它的解码器不驱动 AVAudioEngine —— 发它会把音频挪到不出声的那条路上」*。

## 1. 契约改动（两个仓各一半）

### 网关：每一轮发 `ai.tts.start`

```
ai.tts.start { turn_id, voice_id, sample_rate, codec }   ← 已定义，开始发
<binary audio frames>                                     ← 不变，格式不动
ai.tts.end   { turn_id, completion_status, duration_ms }  ← 已经在发
```

**二进制帧格式一个字节都不改。** 归属由「谁是这个 start 和 end 之间的帧」决定 ——
这正是 `TTSFrameDispatcher` 已经在做的事。

### 客户端：一个真的会出声的 `TTSDecoder`

`TTSDecoder` 是协议，实现换成把 PCM 交给音频引擎的那条路。语义上**等价于今天的
fallback**（`audioEngine.play(frame:)`），只是多了轮次归属。

## 2. 上线顺序：**客户端先，网关后**（关键）

这不是可以随便挑的顺序：

| 顺序 | 结果 |
|---|---|
| **客户端先** | 网关还不发 `ai.tts.start` → 走 fallback → **行为零变化**，可以单独上线、单独验证 |
| **网关先** | 老客户端把音频认领进 dispatcher → 交给不出声的解码器 → **整条音频静音** |

所以：

1. **第 1 步（客户端）**：换上会出声的解码器。**此时行为不变**（没有 start 可认领）。
3. **第 2 步（网关）**：开始发 `ai.tts.start`。客户端从 fallback 切到 dispatcher。
4. **回滚**：任一步出问题，网关停发 start 即可退回 fallback —— 客户端两句都支持。

**没有锁步要求**，因为第 1 步是严格向后兼容的。

## 3. 打开之后，两个 bug 一起解

### a) 打断停不下在途音频（P0-11 主症状）

客户端**知道**自己在播哪一轮（`activeTurnID`），也**知道**自己打断了（它发的
`user.speech.start`）。于是：

```
打断 → dispatcher.interrupt() → stream = .draining(被打断的 turnID)
     → 之后到达的帧：认领，但不播放  ← 这一条已经把缺口堵上
     → ai.tts.end 到达 → stream = .idle
```

**在途帧的缺口就是靠这个关掉的**，而且不需要帧上带任何新字段。

### b) 「音频要等点击才播」（P0-11 的另一半）

今天音频的**出站时机**由 `collectTurn` 收尾决定 —— 一条 61 秒的回复整批到达。
切到 `ai.tts.*` 之后，音频有了**显式的开始与结束**，客户端就具备了「这一轮说到哪了」
的判断依据，而不是只看帧到没到。

**注意**：这不自动修好流式时机 —— 出站时机是网关侧的事。它只是让客户端第一次
**能看见**边界。

## 4. 要定的三件事

1. **`codec` 与 `sample_rate` 填什么。** volc-duplex 今天发的是**重采样到客户端播放
   率的裸 PCM16**（`encodeAudioFrame`）。所以字段应当是 `codec: "pcm"` 加上真实采样率，
   而**不是** `opus`。填错会让客户端去解一个不是 Opus 的负载。
2. **`interrupt()` 之后到 `ai.tts.end` 之间的帧**：今天 `.draining` 会**认领但不播放**。
   确认这是想要的语义（我认为是：那正是「用户在途丢弃」）。
3. **`.draining` 何时结束。** 今天靠 `ai.tts.end`。如果一轮被打断后**永远收不到**
   它（连接断了、回合被放弃），stream 会卡在 `.draining` 把下一轮的音频也吞掉。
   **这是打开这条路径引入的新风险**，需要一条兜底（比如下一个 `ai.tts.start` 到达
   时强制结束上一个 —— 今天 `aiTTSStart` 分支里已经有类似处理，要确认它覆盖 `.draining`）。

## 5. 验证

**先复现再改**（用户要求，也是本仓纪律）：

- 客户端的缺口**已经有复现测试**：`anInterruptDoesNotStopAudioThatHasNotArrivedYet`
  （ios `9fac40e`）。它的断言写成了「若这条**失败**，说明门禁获得了区分能力」。
- **第 2 步的验收就是把那条断言翻过来**：打断后到达的帧必须被丢弃 → **先看它红**
  → 再实现 → 绿。
- 网关侧：构造一轮 → 断言 outbound 里 `ai.tts.start` 出现在该轮第一帧音频**之前**，
  且 `codec`/`sample_rate` 与实际负载一致。

**真机判据**：

1. 让 AI 长回答 → 播放中点开始说话 → **A 立即静**（目标 < 350ms，见 `82_` 引的业界预算）
2. 日志：`tts_first_audio` 出现（今天恒为 0，因为 dispatcher 从没被用上）
3. **反面对照**：不打断的一轮，音频完整
