## 1. 为什么现在轮到它

`meta/docs/30_技术方案/99_WSS系列_18_轮次归属_顺序标识与三条时钟.md` §⑩ 把债按**根因**分了四类，
「**二进制音频帧没有 `turn_id`**」在 **B 类（协议冻结 —— 要版本化才能还）** 里，
并被点名为**本篇指认的头号债**：

> **B 类不还，代理方案就永远需要靠测试守卫撑着。**

§⑪ 把还法放进「**中期（版本化）**」，并说明为什么非它不可：

> **但它是唯一能把代理换回标识的路径** —— 其余都是在代理上加补丁。

以及一条应当被逐字记住的判断标准：

> **每当你发现自己在用「时机」或「顺序」表达「归属」时 —— 记下来，那是一笔债。**
> 它今天能 work（因为有测试守着），但它不会自证，也不能组合。
> **加字段的成本是一次性的；补代理的成本是每次改动的。**

**今天的归属正是「时机」**：客户端看「哪个 `ai.tts.start` 是当前活跃的」（§2.2）。
Stage 3 就是把这一条换掉。

## 2. 事实基线（2026-09-25 逐条核实）

### 2.1 方向 A 的网关侧**已经落地**

`meta 84_` §3.7 写着：

> **但生产路径今天一个 `ai.tts.start` 都不发。**

**【实测】已过期。** volc-duplex 今天在两条路都发：

| 路径 | 位置 | 证据 |
|---|---|---|
| 流式 | `provider_volc_duplex.go:331-341` | `startTurn := first && !s.ttsStarted` → `s.emit(s.ttsStartFrame(turnID))` |
| 批量 | `provider_volc_duplex.go:1023-1024` | `if !interrupted && !ttsStarted && (reply != "" \|\| len(turn.AudioPCM) > 0)` → `append(..., s.ttsStartFrame(turnID))` |

而 `:365-383` 的构造函数注释解释了为什么只有一个构造函数：

> One constructor for both emitters (the streaming path in AssistantAudio and the batch
> path in turnToOutbound) so the two cannot describe the same stream differently —
> **the client keys frames by the turn_id in here**, and a mismatch between the two would
> strand the audio it is supposed to attribute.

字段值也与 `83_` §4 第 1 问的建议一致：`Codec: "pcm"`、`SampleRate: 16000`（**不是** `opus`）。

### 2.2 客户端侧：归属来自「当前活跃的 `ai.tts.start`」

`Shared/FluentWorkCore/Architecture/Middleware/SpeechSessionMiddleware.swift:738-742` 逐字：

> 归属来自「当前活跃的 `ai.tts.start`」——**二进制帧上没有 `turn_id`**。

而 `Shared/FluentWorkCore/TTS/TurnKeyedAudioFrame.swift:9-16` 把这条机制写得更清楚：

> 现状 `WSAudioFrame` 只有 `sequence` 和 `payload`，无法区分哪些帧属于哪一轮对话。
> …… 当后端发送 `ai.tts.start` 时，客户端记录 `turn_id`；
> 后续二进制帧（`case .audio`）**通过归属指针关联到该 `turn_id`**。

**「归属指针」就是 `99_` §⑪ 说的那个「代理」。**

### 2.3 方向 A 的客户端侧**也已经落地**（`99_` §9.4 已过期）

`meta 99_` §9.4 写着：

> 生产 DI 绑的仍是 `MockTTSDecoder`，`EngineBackedTTSDecoder` 已写已测但**未接线**。

**【实测】已过期。** `ios/Shared/FluentWorkCore/Dependencies/AppDependencies.swift:679-690` 逐字：

> 这里曾经有一个 `ttsDecoder` 绑定，指向 `MockTTSDecoder`（只记录、不出声）。
> 2026-09-12 的静音事故就是它：网关一发 `ai.tts.start`，帧被旧派发器认领，音频从此交给一台录音机。
> **Stage 4 把整条并行路径删掉了** —— 现在带轮次归属的帧走 `audioFrameDecoder`（真实解码）
> → `AudioSink.play(pcm:)`（真的出声）。

**【读码】所以方向 A 两侧都通了**，而且是在 Stage 4 里收口的（删掉整条并行路径，而不是把两条路都留着）。

### 2.4 ⚠️ **没有回滚开关** —— 这一条决定 §4 的 Q3

同一段注释接着写（`AppDependencies.swift:684-690`）：

> **没有回滚开关。** 契约 `meta 83_` §2 原写「网关停发 `ai.tts.start`，帧自动退回 legacy 路径，
> 客户端不用改任何一行」—— 那条 fallback 已随 legacy 路径一起删除（`d004869`）：
> 无归属的帧现在被 `TTSPlaybackCoordinator` 判 `.dropped(reason: .unknownTurn)`。
> **网关停发 start 的产物是整轮静音，不是降级出声；要回滚只能回滚客户端提交。**

**【读码】`83_` §2 那张「上线顺序」表的两行前提，今天只剩一行成立：**

| `83_` §2 写的 | 今天 |
|---|---|
| 「客户端先 → 网关还不发 `ai.tts.start` → 走 fallback → 行为零变化」 | ❌ fallback 已删；客户端先走的是**真实解码**那条路 |
| 「网关先 → 老客户端把音频认领进 dispatcher → 交给不出声的解码器 → 整条音频静音」 | ✅ 机理仍在（dispatcher 换成了 `TTSPlaybackCoordinator`），但**方向反了** |
| 「回滚：网关停发 `ai.tts.start` 即可退回 fallback」 | ❌ **整轮静音** |

**这条不是历史考据，它是 Stage 3 的直接约束**：二进制布局是锁步改动（`83_` §0 自己警告过
「两仓锁步、版本错配会让音频整个失效」），而现在**没有任何东西可以让它退回去**。

### 2.5 二进制帧的「升版」**今天没有归属地**

`84_` §3.5 的版本化机制**明确排除**了二进制帧：

> **注意 `ai.tts.audio` 故意不在 v2 的类型清单里** —— 因为它是二进制，不属于「JSON 控制帧」这个集合。
> 有一个测试专门钉住这一点。

而 `99_` §⑪ 对中期路径写的前置是「**帧格式的哈希冻结要正式升版（84 讲版本化机制）**」——
**84 讲的机制恰好覆盖不到它。**【读码】

于是二进制布局今天的实际钉子只有两处，**各自独立**：

| 侧 | 位置 |
|---|---|
| 后端 | `internal/voiceproto/frames.go:179-218`（注释 + `Encode`/`DecodeAITTSAudio`） |
| iOS | `Shared/FluentWorkNetworking/Socket/WSAudioFrameCodec.swift` |

后端那句注释自己承认了这个耦合：

> `// Wire layout matches iOS WSAudioFrameCodec: 4-byte big-endian seq + payload.`

**「靠注释声明两边一致」= 同一份语义两个实现点，且没有东西会在它们分歧时变红。**
这正是本项目反复撞到的形状（`AGENTS.md` §7 R2）。**Stage 3 会新增第三个这样的点**
（两个头的版本），所以 §4 的 Q4 是必须先答的。

#### 2.5.1 ⚠️ 而且这两处**已经分歧了** —— 不是预防性论证

写这份答复时顺手核了 iOS 那份实现，它的注释**两次**声明载荷是 Opus：

| 位置 | 逐字 |
|---|---|
| `WSAudioFrameCodec.swift:5-6` | `The payload is whatever the active ai.tts.start codec says it is — **Opus in the gateway's current shape**, already-PCM16 under RawPCM16FrameDecoder.` |
| `WSAudioFrameCodec.swift:29` | `Binary layout: UInt32 big-endian sequence + **Opus payload bytes**.` |

而网关今天**实测**发的是 `codec: "pcm"`、`sample_rate: 16000`（`provider_volc_duplex.go:377-380`，逐字见 §2.1 的表下方）。

**【读码】所以「同一份布局两个实现点」不是理论风险 —— 它的**语义半边已经错了一次**，
且没有任何东西变红。** 注意 `:5-8` 那段其实**自己察觉到了**这个问题：

> …… The field is named `payload`, not `opusPayload`, so the name stops claiming
> a codec **the decoder is the one to decide**.

它把**字段名**改对了（并留了 `@available(*, deprecated, renamed:)` 的 `opusPayload` 别名），
却把**同一条注释**留在了原地 —— 「改了名，没改话」。这正是本项目认得的那个子型：
**一个从不取真值的判据**（这里是「注释声称的事实」），它静默地为假，而没人会因此被拦下。

**对 Q4 的意义**：它把 Q4 从「建议先补真源」变成「**这个形状已经发生过一次，这次改动会让它从 2 个实现点变成 4 个**」。

## 3. 推荐形状

**与 `25_` §3.3 一致，不改**：

```
现在： [4B sequence][payload]
建议： [4B sequence][4B turn_ref][payload]        ← 仅当 ai.tts.start 带了 turn_ref
```

```
ai.tts.start { turn_id, turn_ref?, voice_id, sample_rate, codec }
ai.tts.end   { turn_id, turn_ref?, completion_status, duration_ms? }
```

- `turn_ref` 是**网关按 socket 分配的单增 uint32**（不是 `turn_id` 字符串）——
  头部保持定长，每帧不浪费。
- 客户端据此建 `turn_ref → turn_id` 映射，`ai.tts.end` **关闭**映射项（否则按 socket 无限增长）。
- **收益**：归属从「控制帧时序推断」变成「数据帧自描述」。`TTSPlaybackCoordinator` 不再需要
  「当前活跃的 `ai.tts.start`」这个**归属指针**（元数据仍需它：`voice_id`/`sample_rate`/`codec`）。
- `ai.tts.end` 也带 `turn_ref`，与 `25_` §3.3 一致。

**唯一与 `25_` 不同的地方在 `?`**：见 Q2。

## 4. 要定的四个问题

### Q1 —— `turn_ref` 的编号域：**每会话，还是每连接？**

**建议：跟 `seq` 同域，即「整条 socket」。而且必须另起一个分配器，不能复用 `SeqAllocator`。**

理由不是偏好，是仓内已有的先例，而且理由同型。`internal/voicegateway/seq_allocator.go:5-27` 逐字：

> **It belongs to the session, not to a provider.**
> The client's barge-in gate drops every frame at or below a watermark, and that watermark
> lives for the whole WebSocket session — it is cleared by start/stopCapture, never between turns.
> So the numbering must be monotonic for as long as the socket is open.
> It used to be a `uint32` field on the provider session … **a transparent reopen built a fresh
> session whose counter restarted at 1, behind a watermark already in the hundreds, and every
> later frame was discarded. The transcript kept working … and all audio was gone for the rest
> of the run** — the "transcript still works, sound is dead" device report.

`turn_ref` 面对的是**同一类**事故：客户端按它建映射，所以 provider 透明重开后计数器从 0 重来
会让新轮的帧命中旧轮的映射项。**同一个理由给出同一个答案。**【读码】

**注意**：`SeqAllocator` 按**帧**递增，`turn_ref` 按**轮**递增，所以是**另一个**分配器 ——
复用会让 seq 跳号，而 seq 是 barge-in 水位线的依据。

### Q2 —— `ai.tts.start` 的 `turn_ref` 是否必需？

**建议：可选。缺席 = 旧布局（4 字节头）。**

`25_` §3.4 倾向必需，理由是「没有它帧就没法归属，与 `voice_id` 那类纯日志字段性质不同」——
这个理由**成立**，但必需会丢掉一个更值钱的东西：

1. **它同时是「布局开关」。** 必需的话，「这一轮用哪个头」就无法表达，只能靠两端各自的版本号
   硬对齐 —— 而那正是锁步。
2. **D5 的教训**（`25_` §3.4 自己引的）：必需字段的爆炸半径。
3. **它是唯一能造出回滚开关的办法** —— 见 Q3。

**代价要写下来**：客户端过渡期要同时支持两种头，所以需要一个**明确的退役日期**，
否则那个 `if` 会永远留着。建议在契约里写死「网关切到带 `turn_ref` 后，旧头路径保留 N 个版本」。

### Q3 —— 过渡期

**建议：客户端先（容忍两种），网关后；回滚 = 网关不再置 `turn_ref`。**

| 顺序 | 结果 |
|---|---|
| **客户端先** | 它学会了「`ai.tts.start` 带 `turn_ref` 就用 8 字节头，不带就用 4 字节」。老网关不置 → **走旧布局，行为零变化**，可以单独上线、单独验证 |
| **网关后** | 开始置 `turn_ref` 并改发 8 字节头。客户端从旧头切到新头 |
| **回滚** | **网关不再置 `turn_ref`** → 客户端退回 4 字节头 → 出声正常 |

**这恢复了 §2.4 里那个今天不存在的回滚开关**，而且**不需要复活 `handshake`**
（`25_` §3.4 第 3 问本来把复活 `handshake` 算作走协商的额外工作量；走这条路不需要它）。

**为什么不能反序（网关先）**：老客户端会把 `raw[4:8]` 当成载荷的前 4 字节 —— 每帧开头多出
两个样本，表现为每帧一次咔哒声，而不是整轮静音。**它不静音，所以更难发现。**【推断】

### Q4 —— 「帧格式正式升版」落在哪？（`99_` §⑪ 的前置，`84_` 覆盖不到）

**建议：在 `fluentwork-infra/schemas/transport/` 下加一份独立的二进制帧布局产物，
并用 sha256 冻结（照 v1 那套）。**

理由见 §2.5：今天的布局只有「后端一行注释 + iOS 另一份实现」，**没有任何东西会在两者分歧时变红**。
Stage 3 会把它变成「两个头 × 两个仓 = 四个实现点」，所以先有真源再动手。

**这一条不做也不是不能改代码**，但那样这次改动会**新增**一个「同一份布局两个实现点」，
而 §1 引的那句判断标准说的正是这个：*加字段的成本是一次性的；补代理的成本是每次改动的。*
**如果这次不补，下一次还得补。**

## 5. 代价与风险

| | |
|---|---|
| 头部 4 → 8 字节 | 按 100ms 帧 / 16kHz 单声道 PCM16 算，载荷 3200 字节，开销 **+0.125%**。可忽略【推断】 |
| 客户端过渡期两套头 | 需要退役日期（Q2 的代价） |
| 映射项泄漏 | 若某一轮**收不到** `ai.tts.end`（连接断、回合被放弃），`turn_ref → turn_id` 项不会关闭 → 需要兜底：**下一个 `ai.tts.start` 到达时强制关闭上一个**。**这与 `83_` §4 第 3 问是同一类风险**（`.draining` 何时结束），两条要一起看 |
| 无回滚开关（今天） | Q3 的方案**顺带修掉它**；但在网关切换之前，客户端仍然没有开关 |
| 锁步风险 | Q3 之后**不再是锁步**（客户端先的那一步向后兼容）—— 这是本文对 `83_` §0「两仓锁步」那判断的修正 |
