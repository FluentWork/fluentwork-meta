# FluentWork 深度思考（Thinking）场景与落地讨论

> **文档性质**：技术 + 产品边界讨论文档。  
> **状态**：仅沉淀结论与可选方案，**暂不在代码仓落地**。  
> **关联**：`34_FluentWork火山引擎选型与开通清单.md`、backend `docs/14_B8_…` / `docs/15_B8_Ark_live_诊断记录.md`  
> **日期**：2026-08-31

## 1. 结论先说

| 问题 | 结论 |
|---|---|
| 当前 B8 关闭深度思考，是否**有必要**？ | **有必要**。在现有 `fw-review-refine` 绑定 thinking 能力模型、且产品硬约束「评价生成 ≤ 15s」的前提下，不关 thinking 会系统性撞红线。 |
| 产品需求里，是否**明文要求**深度思考？ | **没有**。PRD / 技术方案要求的是：结构化评价与炼化、引用原句、异步就绪与体验红线；**不要求**把模型推理过程展示给用户。 |
| 是否存在「值得开 thinking」的业务场景？ | **有潜在场景**，但都属于 **MVP 之后 / 可选增强**，不是当前 `B8` 主路径。 |
| 若开 thinking，推理内容能否输出到产品？ | **可以技术上拿到**（如 `reasoning_content`），但**默认不建议直接对用户展示原文**；若要展示，需单独产品化（摘要、可折叠、隐私与文案审核）。 |

**当前工程默认（已落地，本文件不改）**：`thinking.type = disabled`，保证 B8 live 约 7–9s、过 B15，且对齐 P90 ≤ 15s。

## 2. 深度思考在这里指什么

本文「深度思考 / Thinking」特指火山方舟（Ark）侧一类能力：

1. 模型在正式 `content` 之外，可产生 **`reasoning_content`（或等价 reasoning tokens）**  
2. 请求可用参数控制，例如：
   - `"thinking": {"type": "disabled"}` — 关闭  
   - 开启 / 默认开启 — 先推理再答（具体枚举以方舟当期 API 为准）  
3. 对 FluentWork 的直接影响是：**墙钟时延显著变长、token 成本上升、与 `json_object` / Schema 强约束组合时稳定性变差**

它**不是**产品文案里的「认真分析你的表达」——后者是 UX loading 文案，可用非 thinking 模型完成。

## 3. 为什么 B8 现在必须关 Thinking

### 3.1 产品与技术方案硬约束

| 来源 | 约束 |
|---|---|
| PRD 体验红线 | 评价生成 ≤ **15 秒**，超限告警 |
| 后端方案 §5.2 | 评价任务 **P90 ≤ 15s**；评价+炼化合并一次旗舰调用 + JSON Schema |
| UI 回顾页 | 结束会话后立即进回顾；骨架 → **≤15s** 淡入评价/对照/炼化；失败保留转录 + 重试 |
| B15 / Prompt | 强结构化、强制引用原句、枚举受控；「宁可少而准」 |

用户感知的是「分析中…」，不是「模型在内心独白」；**时延预算全部花在可用 JSON 产物上**，而不是 reasoning 链路。

### 3.2 Live 证据（2026-08-30）

见 backend `docs/15_B8_Ark_live_诊断记录.md`：

| 条件 | 现象 |
|---|---|
| thinking 默认开 + 完整 review JSON | 常 **45–120s 仍 0 字节** / 超时 |
| 同 endpoint 最小 `PONG` | ~2–3s 可通 → **不是链路彻底不通** |
| `thinking.disabled` + B15 smoke | ~**7–9s** PASS，`reasoning_tokens=0` |

因此：关闭 thinking 是 **SLA 对齐 + 稳定性** 决策，不是「模型能力不够所以关掉」。

### 3.3 与「旗舰档」选型不矛盾

`34` 文档要求评价/炼化用**旗舰档**（指令遵循、长上下文、结构化稳）。  
Thinking 是旗舰模型上的**可选推理模式**，不是旗舰档的同义词。  
**关闭 thinking ≠ 降档到小模型**；当前仍是旗舰 endpoint + 结构化输出。

## 4. 产品场景对照：要不要 Thinking

按「是否服务用户直接可见价值」与「时延预算」打分。

| 场景 | 产品要求（摘要） | 时延预算 | 是否需要 Thinking | 建议 |
|---|---|---|---|---|
| **B8 评价 + 炼化（主路径）** | 三层评价、双栏对照、炼化卡；引用原句；JSON | P90 ≤ 15s | **不需要** | 保持 `disabled` |
| **B7 命中匹配** | 旁路；失败可跳过 | ≤ 800ms | **禁止** | 小模型 + 硬超时 |
| **闪测判定** | 语义是否答对 | 约 1–3s；超时待确认 | **禁止** | 小模型 |
| **文本降级对话** | 能聊即可 | 尽量低 | **禁止** | 小/中档 |
| **说的房间主对话** | 首响 P90 ≤ 1.5s | 实时 | **禁止** | 端到端语音 / 低时延文本 |
| **每日一读 / 话题卡** | 质量优先、可异步 | 通常可 >15s（非回顾关键路径） | **可选** | 默认关；质量抽检不过再开灰测 |
| **人工抽检 / 离线评测（B15 扩维）** | 解释「为何判这个问题」 | 离线分钟级可接受 | **可选** | 仅批处理，不对在线用户 |
| **客服/教研「评价解释」**（未立项） | 给教研看推理摘要 | 非用户主路径 | **可选** | 内网工具，不进 App |
| **争议句二次精修**（未立项） | 用户点「再分析一遍」 | 可单独约定 30–60s | **可选** | 显式二次动作，非默认 |

**产品层一句话**：MVP 用户价值在「原句 → 更地道版本」与可入库话术块，**不在展示 CoT**。深度思考不是当前 wow moment 的必要条件。

## 5. 若产品要开 Thinking，怎么落地（方案级，未实施）

以下仅为讨论草案，**不改现网默认**。

### 5.1 原则

1. **默认关、显式开**：主路径 `disabled`；仅白名单场景 / 灰度开关开启。  
2. **时延与体验绑定**：开 thinking 的入口必须配套「有预期的等待」或「非阻塞二次生成」。  
3. **产物分层**：`content`（结构化业务 JSON）与 `reasoning`（过程）分字段存储与权限。  
4. **成本可观测**：`ai_cost_logs` 区分 `reasoning_tokens`（若 API 提供）与 completion tokens。

### 5.2 推荐落地形态（从稳到激进）

#### 形态 A — 仅服务端增强质量（推荐作第一候选）

- 请求：thinking **enabled**（或 auto）  
- 客户端：仍只消费校验后的 review/refine JSON  
- UX：仍走现有骨架 ≤15s；**若超时 → 失败态 / 重试 / 或自动降级到 disabled 再打一枪**  
- 适用：质量抽检明显差、且愿意用「偶发变慢 + 降级」换准确度  

#### 形态 B — 用户主动「深度再分析」

- 回顾页增加次级动作：「再深入分析一次」（非默认）  
- 文案预期：**约 30–60 秒**（具体数用 live 标定）  
- 第一次结果仍用 disabled 快速出；深度结果覆盖或并排「精修版」  
- 适用：高价值用户、长会话、付费档（若未来订阅分层）  

#### 形态 C — 推理内容产品化展示（谨慎）

- 将 `reasoning_content` **摘要**为「分析说明」（短中文，非原文 CoT）  
- UI：折叠区「本次评价依据（可选）」；默认收起  
- **不要**原样展示英文/内部思维链（噪声、幻觉、隐私、品牌风险）  
- 需单独 Prompt：「根据 reasoning 写 ≤80 字用户可读说明」，再过审核词表  

#### 形态 D — 换非 Thinking 旗舰 Endpoint（工程备选）

- 若控制台可提供「同档、无 thinking / O 版低时延」endpoint：主路径换 ep，从根源去掉参数博弈  
- 与 `34`「旗舰给评价炼化」一致，且更干净  

### 5.3 与渐进加载的配合

现有 UI 已定义两层到达（转录 3s 内 / 评价 ≤15s）。若引入 thinking：

| 策略 | 做法 |
|---|---|
| 硬守 15s | thinking 仅允许在「预计 P90 仍 ≤15s」的配置下开启；否则禁止 |
| 放宽档位 | 产品改红线（例如深度档 P90 ≤ 45s），并改 UI 预期文案与进度 |
| 双轨 | 快轨 disabled（≤15s）+ 慢轨 thinking（后台续写，推送/轮询第二层「精修已更新」） |

**未改 PRD 前，不得把默认主路径改成 >15s。**

## 6. 等待时延与超时：建议配置项（讨论稿）

> 下列为建议配置键名与量级，便于以后实现；**当前代码未落地这些开关。**

### 6.1 建议配置面

| 配置项 | 含义 | 建议默认 | 备注 |
|---|---|---|---|
| `ARK_REVIEW_THINKING_MODE` | `disabled` / `enabled` / `auto` | `disabled` | 主路径 |
| `ARK_REVIEW_HTTP_TIMEOUT` | 单次 HTTP 客户端超时 | `20s`～`30s` | 须 **≥** 任务 SLA，且 **≤** job timeout |
| `ARK_REVIEW_SLA_MS` | 告警阈值（对齐产品 15s） | `15000` | 超限打点/告警，不必立刻失败 |
| `ARK_REVIEW_JOB_TIMEOUT` | worker 单 job 上限 | `60s`（现状量级） | 含重试预算要另算 |
| `ARK_REVIEW_THINKING_HTTP_TIMEOUT` | 仅深度档 | `45s`～`90s` | 仅形态 B/C |
| `ARK_REVIEW_THINKING_SLA_MS` | 深度档体验预期 | `45000`～`60000` | 必须与 UI 文案一致 |
| `ARK_REVIEW_FALLBACK_ON_TIMEOUT` | 超时是否再打一枪 disabled | `true`（建议） | 避免整页失败 |
| `ARK_REVIEW_EXPOSE_REASONING` | 是否落库/下发 reasoning | `false` | 默认不落用户可读库 |

### 6.2 超时分层（推荐语义）

```
用户感知 SLA（15s）  ≤  HTTP timeout  ≤  Job timeout
       │                    │                 │
   告警 / UI 预期        取消请求           任务失败/重试
```

- **SLA**：产品红线，超时告警 + 可选降级，不等于立刻给用户失败页。  
- **HTTP timeout**：避免 worker 挂死在 `awaiting headers`。  
- **Job timeout**：整条管线（含写库、cost）上限；须留给 Fail/Complete。

Thinking 开启时，三者必须**一起上调**，并改 UI「正在深入分析，约需 XX 秒」；只改模型参数、不改超时与文案，会造成「静默等待」——与 PRD A1/回顾页「有预期 loading」纪律冲突。

### 6.3 观测

至少盯这些字段（现有 `duration_ms` 已可起步）：

1. `review.generate.duration_ms` P50/P90  
2. 是否 `thinking_enabled`  
3. `tokens_in` / `tokens_out` /（若有）`reasoning_tokens`  
4. `fallback_stub` / `fallback_disabled_retry` 次数  
5. 用户侧：回顾页从进入到第二层到达的时长

## 7. 深度思考内容能否「输出」到产品

### 7.1 技术上

- 开启 thinking 时，响应里可能出现 **`reasoning_content`**（或流式 reasoning 增量）。  
- 业务 JSON 仍应只信任 **`message.content`**，并继续走 **B15 / Schema 校验**。  
- Reasoning **不能替代**结构化 `review` / `refine`；校验失败仍应失败或降级。

### 7.2 产品上（建议政策）

| 做法 | 建议 |
|---|---|
| 把完整 CoT 直接展示在回顾页 | **不建议**（噪声、不稳定、可能含不当推断） |
| 服务端日志保留 reasoning 原文 | **仅调试环境 / 采样**；生产注意隐私与日志体积 |
| 落库 `ai_debug_traces` 供教研 | 可选，权限与保留期单独立项 |
| 生成「用户可读分析说明」短摘要 | 可选增强（形态 C），需文案与审核 |
| 对外 API（`GET …/review`）返回 reasoning | **默认否**；若有，独立字段且默认不返回 |

### 7.3 合规与品牌

- Reasoning 可能包含对用户能力的主观判断，直接展示伤害「先肯定后改进」的展示纪律。  
- 若未来展示，应走与评价卡同一套语气约束（Prompt 文档纪律），而不是裸 CoT。

## 11. 一句话备忘

> **关掉深度思考，是为了守住「评价 ≤15s + 结构化可用」这条产品红线；产品没有要求展示思考过程。若未来要深度思考，应做成可配置的慢轨或二次动作，并单独设计超时、降级与（可选的）摘要化展示——而不是改回主路径默认开启。**
