# WSS 系列 11 · 怎么测试一条 WSS 链路

**版本**：V1.0
**日期**：2026-09-11
**定位**：这一层怎么测。不是"测试很重要"这类空话 —— 而是本项目在这件事上具体做了什么、每一招解决什么问题、以及**哪里还是空的**。
**对应上游文档**：[88 可观测性与健壮性](88_WSS系列_07_可观测性与健壮性.md)（那是"怎么看见"；本篇是"怎么证明"）
**变更说明**：首版。补完本系列在测试策略上的缺口。V1.1：红验证与三种盲区改为指向 89，本篇只留落地后果与测试空白。

## ① 本篇回答什么

**一个问题**：一条 WebSocket 链路，怎么测？

**读完后你能**：

- 说清为什么"规则要住在能被单独调用的地方"
- 说清测试替身**必须保真**的那个点在哪 —— 以及本项目替身**不**保真的那一半
- 知道本项目在这一层的**空白**在哪里（真实 socket 零覆盖）
- 红验证和三种"看起来在测"的形状见 [89 六](89_WSS系列_08_方法论_遇到同类场景怎么想.md)，本篇不重复

## ② 概念

**纯值类型。** 不持有连接、不发起 I/O 的类型 —— 输入进去，输出出来。它是可测性的基础。

**测试替身（test double）。** 替代真实依赖的对象。它最大的风险是**和生产行为不一致** —— 于是测试全绿，线上照坏。

**契约测试。** 钉住"线上字节长什么样"的测试。它防的不是逻辑错误，是**两端各自演化导致的静默不兼容**。

**红验证。** 写完测试后**故意把实现改坏**，看红的是不是预料的那条。

## ③ 约束与推导

### 3.1 第一原则：把规则从管道里拉出来

一条 WSS 链路最难测的部分是**管道本身** —— 它要真实网络、真实时序、真实对端。

**本项目的对策不是"想办法测管道"，而是"让尽可能多的东西不住在管道里"**：

```mermaid
flowchart TB
    subgraph pipe["住在管道里（难测）"]
        P1["连接建立"]
        P2["收发循环"]
        P3["心跳定时"]
    end
    subgraph pure["拉出来的纯值类型（易测）"]
        R1["丢弃策略<br/>给定序号和水位线，该丢吗"]
        R2["丢弃上报<br/>什么时候报、报什么"]
        R3["时钟估计<br/>给定三次采样，偏移是多少"]
        R4["重采样<br/>分块喂进去，输出对不对"]
    end
    pipe -.->|"只负责决定<br/>样本从哪来"| pure
```

**这条原则的检验方式很简单**：问一句 —— **"这条规则能在没有 socket 的情况下被调用吗？"**

**能，就应该把它拉出来。** 拉出来之后，它不但可测，而且测起来**快、稳、能覆盖边界** —— 而那三样恰恰是"跑真连接"永远给不了的。

### 3.2 第二原则：替身必须保真 —— 但只在**一个**点上保真

测试替身最大的谎言是"看起来像"。本项目有一个具体的做法值得学：

> **替身注入音频时，走的是和生产完全相同的那道丢弃闸门。**

也就是说，替身**不模拟**丢弃行为 —— 它**调用同一个实现**。于是"打断之后音频被正确丢弃"这件事，在替身上测出来的结论，对生产也成立。

**但保真到这里为止 —— 而且差的那一点恰好很关键**：

| | 替身 | 生产 |
|---|---|---|
| **帧该不该丢** | ✅ 跑同一个实现 | ✅ |
| **丢了之后上报** | ❌ **没有** | ✅ 会发诊断事件 |

**生产的传输层在丢弃时还会发一条诊断事件**（开头一次、结束一次，带上丢弃计数）—— 替身不复现这个。

**为什么这个差别不能忽略**：它意味着 **"丢弃是否可观测"这件事，在替身上测不出来**。而这正是排查手册里"有声音但缺一段"那个症状**首先要看的东西**。

换句话说：**替身能证明"丢得对"，不能证明"丢了之后你知道"。**

**"只在关键点上保真"的判据是**：*这个替身要替的那件事，跑了真实实现吗？*

- 要替"音频会在打断后停止播放" → **必须**跑真实的闸门 ✅
- 要替"丢弃会被上报" → **没做到** ⚠️
- 要替"网络会抖" → 模拟就够了，反正真实网络也不可复现

**所以替身的边界要写在注释里**，否则用久了会忘记哪一半是保真的。

### 3.3 第三原则：把不可能断言的东西变得可断言

有些东西天然不可断言 —— 比如"耗时"。而这个项目的核心指标恰恰是耗时。

**做法是注入**：

| 注入什么 | 换来什么 |
|---|---|
| **时钟** | "首响是 250 毫秒"从"大于零"变成**精确值** |
| **当前时间函数** | 静默保活的阈值判断可以精确构造 |
| **探测函数** | "上游探测失败"可以被构造出来，不用真等 |
| **重开函数** | "重开之后再失败"的路径可以被走到 |

**这条原则的一般形式**：

> **任何"读系统时钟"或"发起外部调用"的地方，都是一个测试的断点。** 把它变成可注入的参数，那条路径才可测。

**代价**：这些参数在生产代码里看起来是"多余的抽象"。它们的价值只有在写测试时才显现 —— 所以**注释里要写明它们是测试缝**，否则会被当成沉积清掉。

### 3.4 第四原则：钉住线上的**字节**，不只是行为

两端各自演化时，最危险的不是逻辑错了，而是**逻辑都对、但对不上**。

**本项目的三种钉法**：

| 钉什么 | 怎么钉 | 两端都有吗 |
|---|---|---|
| **单个帧的线上字节** | 用一段**写死的 JSON 字面量**做断言，两端共用同一份样例 | ✅ 两端 |
| **整个协议版本** | 服务端用**哈希**钉住 schema 文件，改动即失败 | ⚠️ **只有服务端** |
| **schema 的结构** | 客户端钉的是**结构**（标题、定义、枚举、必填项），不是字节 | ⚠️ 只有客户端这样做 |

**哈希冻结那一招值得单独说**：它把"我们承诺这个版本不再变"从一句口号变成了**一条会失败的测试**。冻结一个协议版本如果不配一条这样的测试，它就只是文档里的一句话。

**但要注意它的覆盖面是不对称的**：

- **服务端钉的是字节** —— 连一个空格的改动都会红。
- **客户端钉的是结构** —— 加一个字段、改一个枚举会被发现，但格式变化不会。

**这个不对称本身合理**（客户端不拥有 schema，钉结构足够挡"两端语义漂移"），**但它意味着**：*"两端都冻结了"这个说法不成立 —— 只有一端冻结了字节，另一端冻结的是形状。*

### 3.5 红验证与三种盲区 —— 方法见 89

定义、三种形状、修法见 [89 六](89_WSS系列_08_方法论_遇到同类场景怎么想.md)。本篇只钉两条落地后果：

- **全绿比红错更值得警惕。** 本项目传输层最大的空白（⑤ 陷阱一）就是这个形状：破坏「真实 socket 连接建立」，没有任何测试会红。
- **替身保真的边界对应「看起来在测」。** 3.2 的替身能证明"丢得对"，不能证明"丢了之后你知道"。排查手册里「缺一段先看丢弃上报」这件事，替身上测不出来。

## ④ 本项目的落地

| 手段 | 位置 |
|---|---|
| 纯值类型（丢弃策略 / 上报规则 / 时钟估计） | `AudioFrameDropGate.swift` · `ClockOffset.swift` |
| 保真的测试替身 | `InMemorySocketTransport.swift` —— 音频注入走**生产同一条**闸门 |
| 事件流可单独构造 | 传输层的 `makeEventStream()` 是 `static`，**就是为了让测试能直接调它** |
| 注入时钟 | `SpeechSessionTimingsRecorder` 的 `clock` 参数 |
| 注入时间 / 探测 / 重开 | 服务端 Provider 的三个函数型 seam |
| 契约测试 | 两端共用的线上字节样例 |
| 协议冻结 | schema 的**哈希**断言（**只有服务端**；客户端钉的是结构） |
| 保留旧实现作参照 | 重采样测试里留着一份**旧实现原文**，用来证明"流式与批量逐字节相同" |
| 内部测试 | 去重日志、上游自动机等不导出的逻辑，用同包测试覆盖 |

**"保留旧实现作参照"这一招值得单独说**：

证明"新实现和旧实现等价"时，**旧实现必须作为第二份代码存在于测试里** —— 否则"没改一个字节"这句话无从谈起。把它删掉，等价性就成了自说自话。

## ⑤ 代价与陷阱

**陷阱一：这一层最大的空白 —— 没有任何测试碰过真实的 socket。**

已核实：**全仓没有任何地方构造真实的 `URLSessionWebSocketTask`**，也没有协议级 stub。传输层只通过两条路径被覆盖：它自己那个可单独构造的事件流，和它委托出去的那些纯值类型。

**这意味着什么**：

| 被覆盖的 | 没被覆盖的 |
|---|---|
| 收到消息之后的**处理** | 连接**建立**（含握手时序） |
| 纯规则 | 接收循环本身的**生命周期** |
| 事件流的缓冲策略 | 取消、重连、析构 |
| 错误**映射** | 真实的网络错误形态 |

**这个空白是已知的，不是疏忽** —— 但它的代价是具体的：**"接收循环读不到消息"和"重连路径"这两类问题，只可能在真机上第一次暴露。**

**陷阱二：替身的保真度是**局部的**，而人会忘记边界。**

`InMemorySocketTransport` 在"丢弃**判定**"上保真，在"丢弃**上报**"和别处都不保真。**危险在于：用久了会忘记哪些地方不保真**，于是拿替身上的结论去推断真实网络行为 —— 比如以为"丢弃是可观测的"已经被测过了。

**对策是在替身的文档注释里写明"我保真什么、不保真什么"** —— 让边界可见。

**陷阱三：时钟注入用不好，会测出"永远正确"的测试。**

注入了时钟之后，所有时间都由测试决定。如果测试没**推进**时钟就断言耗时，会得到一堆零 —— 而零永远是"小于预期"的。

**对策**：断言耗时的地方，必须显式推进一个**非零**的量，并且断言**精确值**。断言"大于零"等于没断言。

**陷阱四：哈希冻结的失败信息不友好。**

协议版本被哈希钉住之后，一次无意的格式化改动会让测试变红，而错误信息只是一个哈希不匹配。**下一个人会倾向于直接刷新哈希** —— 而那条注释明确写着"不要刷新它"。

**对策**：注释要**写在会看到它的地方**（测试文件里，而不是别处的文档里），并写清"该往哪个新版本加字段"。

## ⑥ 自检

1. 为什么"把规则从管道里拉出来"比"想办法测管道"更有效？检验方式是什么？
2. 测试替身应该在什么点上保真？判断依据是什么？
3. 为什么"注入时钟"能让一个数字可断言？不注入会失去什么？
4. 哈希冻结一个协议版本，防的是什么？只写文档不写测试会怎样？
5. 红验证里，"全绿"为什么比"红错了"更值得警惕？它和本项目哪块测试空白是同一形状？（方法见 89）
6. 证明"新实现和旧实现等价"时，为什么旧实现必须留在测试里？
7. 本项目在这一层**最大**的测试空白是什么？它让哪类问题只可能在真机上暴露？

## ⑦ 速查

| 原则 | 一句话 |
|---|---|
| **拉出来** | 规则不住在管道里 —— 问"这条规则能在没有 socket 时被调用吗" |
| **保真** | 替身只在关键点上跑真实实现（本项目：音频注入走生产同一条闸门） |
| **可断言** | 时钟、时间、外部调用，全部可注入；否则数字无法断言 |
| **钉字节** | 写死的线上样例（两端）+ schema 哈希冻结（**只有服务端**）；客户端钉的是结构不是字节 |
| **红验证** | 方法见 89：破坏实现，看**是哪条**红。本篇的落地：真实 socket 零覆盖 = 砍那一刀会全绿 |
| **三种盲区** | 断言症状 · 等价性测试对边界盲 · 只测正向 —— **定义见 89 §6.2** |
| **旧实现** | 证明等价时，旧实现必须作为第二份代码留在测试里 |
| **最大空白** | **没有任何测试构造过真实 socket** —— 连接建立与接收循环的生命周期未被覆盖 |
| **替身边界** | 保真是局部的：替身共享了丢弃**判定**，但**没有**共享丢弃**上报** —— 边界要写在注释里 |
| **注入时钟的坑** | 不推进时钟就断言耗时 = 断言零 —— 必须推进非零量并断言精确值 |
