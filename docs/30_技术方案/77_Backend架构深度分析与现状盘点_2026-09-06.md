### 2.3 handler.go 核心结构(19,935 bytes)

**5 个核心职责**:
1. **WSS 握手 + ticket 消费**(consumer.Consume → ConsumedTicket{SessionID, UserID})
2. **帧分发循环**(ReadFrame → 类型分发 → Provider.HandleClientControl/Audio)
3. **sessionRuntime 状态机**(broken / warnDedup / activeTurnID / seq)
4. **BadgeEmitter 协作**(corpus 命中检测 → feedback.badge)
5. **错误帧 + 日志去重**(5s 窗口 + 每 10 次摘要)

**B15 关键变更**(已 merge):
- `rt.broken` 守卫:HandleClientAudio 失败后,后续 binary 帧直接 return,不再调 writeJSON
- `warnDedup` 字段:同 key 5s 窗口内合并,第 10/20/30 次输出摘要
- 始终发送 `ai.turn.end`(即使 outcome≠ok,让 iOS 状态机能离开 .processing)

### 2.5 voicepoc/volc_duplex.go 核心结构(27,465 bytes · 最重的单文件)

**3 个核心抽象**:

```go
type DuplexSession struct { ... }       // 一次 duplex 长连接封装
type TurnOutcome string                  // 4 态枚举
type TurnResult struct { ... }           // 单 turn 观测
type Window struct { ... }               // 注入窗口分析(同 turn / 跨 turn 命中率)
```

**4 态 outcome**(已 merge):
```go
TurnOutcomeOK      = "ok"      // response.done 有内容
TurnOutcomePartial = "partial" // wait 过期有 progress 但无 done
TurnOutcomeTimeout = "timeout" // wait 过期零 progress
TurnOutcomeError   = "error"   // provider error / recv failed
```

**collectTurn 状态机**(B15 修复):
- **超时路径**:`waitAfterCommit=60s` 后,显式 `outcome=timeout`(修复前是 `outcome=ok`)
- **错误路径**:recv failed → `outcome=error`(非 `outcome=ok`)
- **进度路径**:有 ASR 但无 `response.done` → `outcome=partial`

## 十一、重点难点剖析(8 项)

### 11.1 🔴 Provider 接口稳定性

**现状**:`VoiceProvider` + `VoiceProviderSession` 接口已冻结,3 个实现(Mock / DevEcho / VolcDuplex)都满足。

**难点**:
- **新 Provider 接入成本**:OpenAI Realtime、Azure Speech 等需要重写 `HandleClientAudio`(音频格式差异)
- **跨 Provider 抽象**:不同 provider 的 turn 概念不同(Volc 无 turn 概念,需要主动合成)
- **未来扩展**:B17 TTS Provider 是 1+N fallback(主 + 备),需要 Provider 链式调用

**建议**:
- B17 启动时把 `VoiceProvider` 升级为 `VoiceProviderChain`(主备自动切换)
- 在 `provider_factory.go` 增加 `NewChainProvider(primary, fallbacks)` 工厂

### 11.2 🔴 sessionRuntime 状态机(在 handler.go 中)

**现状**:`sessionRuntime{broken, warnDedup, activeTurnID, seq}` 字段,无独立 state machine。

**难点**:
- **broken vs warnDedup 互相干扰**:broken 后 warnDedup 是否继续累计?
- **并发安全**:当前无 mutex,handler 是单 goroutine 但 sessionRuntime 字段被多个回调访问
- **测试覆盖**:`handler_b15_test.go` 覆盖了基础场景,边界 case(rt.broken + warnDedup 同时触发)未覆盖

**建议**:
- W4 启动 `B16 AIOrchestrator` 时,把 sessionRuntime 拆为独立结构体
- 增加 mutex 或 atomic 字段

### 11.3 🔴 Volc SDK 升级风险

**现状**:Volcengine Seeduplex v1.2.6.0 已封装在 `voicepoc/volc_duplex.go`。

**难点**:
- **SDK 升级窗口**:Volcengine 不定期升级 SDK,新版本可能 breaking change
- **凭证变更**:C-2 火山 TTS 独立凭证 9/10 到位,B17 启动时需要重新验证
- **私有 API**:Volcengine 的 `X-Tt-Logid` header 是非公开接口,升级可能移除

**建议**:
- W3 启动包中明确:Volc SDK 升级在 W6 集中处理(避开 V2.0 启动周)
- 关键字段(log_id / X-Tt-Logid)在升级后回归测试

### 11.4 🟠 MySQL schema drift 风险

**现状**:4 个 V2.0 迁移(0008-0011)已就绪,但 production 数据库是否已 apply 不确定。

**难点**:
- **staging vs production 差异**:staging 已 apply,production 可能漏 apply
- **0012 待 V2.0 启动时创建**:B22 启动时需要先 apply 0012 再做代码改动
- **回滚成本**:V2.0 迁移都含 `.down.sql`,但回滚后丢失数据

**建议**:
- W3 启动前(9/13)做一次 production schema audit
- B22 启动 PR 包含「0012 + code」原子提交

### 11.5 🟠 Provider 链与 fallback 策略(B17)

**现状**:`provider_factory.go` 仅支持单 provider 实例。

**难点**:
- **fallback 触发条件**:QPS 限流 / 网络超时 / 凭证失效 如何区分?
- **fallback 状态保持**:切到 fallback 后,session 上下文(turn_id / corpus hit)如何保持?
- **回切主 provider**:fallback 恢复后何时切回主?

**建议**:
- B17 启动时设计 `ProviderHealthState` 结构(连续失败次数 / 最后成功时间)
- fallback 后不主动回切,等下一次 session 启动时用主

### 11.6 🟠 TTS Provider 抽象边界(B17)

**现状**:voicepoc 只封装了 Volc Duplex 内置 TTS;B17 要新增独立火山 TTS provider。

**难点**:
- **音频格式**:Volc Duplex 内置 TTS 输出 Opus,独立火山 TTS 可能输出 PCM/MP3
- **流式推送**:B17 需要流式推送,但 SDK 是否支持 chunk-level streaming?
- **音色表**:D-2 已拍板 4 个音色,但需要验证 SDK 是否都支持

**建议**:
- B17 启动包明确:统一输出 Opus,通过 `opus_encoder.go` 二次编码
- 流式推送通过 SDK 的 chunk callback 实现(每 20ms 一个 callback)

### 11.7 🟡 跨仓测试覆盖率

**现状**:backend 7,043 行测试 / 7,951 行生产 = 88.6% 测试/生产比。iOS 6,179 行测试 / 7,043 行生产 = 87.7%。

**难点**:
- **集成测试分散**:`cmd/integration-voice-gateway` 是独立的 cmd,非 CI 必跑
- **冒烟脚本未串联**:`smoke-*` 6 个脚本独立,无端到端串联
- **跨仓 e2e 缺失**:无 iOS 真机 × backend 集成的 e2e 测试框架

**建议**:
- W3 末(9/20)落库端到端冒烟脚本 `scripts/e2e/w3-smoke.sh`
- W5(B18 接通后)建立跨仓 e2e 测试框架

### 11.8 🟡 AI 成本记账准确性(B8 followup)

**现状**:`aicost/RecordCostTx` 已实现 atomic write + Ark pricing。

**难点**:
- **Ark 价格表**:D-1 已拍板,但实际价格可能浮动,需要季度更新
- **depth 思考异步成本**:异步任务的成本如何归集?
- **失败调用成本**:provider error 时是否计入成本?

**建议**:
- W4 启动 B18 时,把 aicost 价格表抽到 `internal/config/ark_pricing.go`
- 失败调用计入成本(0.5x)以反映真实开销
