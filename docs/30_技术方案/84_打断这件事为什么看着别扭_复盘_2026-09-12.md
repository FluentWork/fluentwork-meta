# 打断这件事，为什么这个解法看着不协调

**日期**：2026-09-12
**状态**：复盘。**当晚的改动全部回滚**（backend `cad64bd` / `1ceeb3f`，ios `29e61d2` 的接线），解码器与测试留在树里。
**触发**：接上方向 A 之后真机**完全没有声音**、说话后停在「识别中」。

---

## 1. 先说回滚了什么，以及我确定知道了什么

| 改动 | 处置 |
|---|---|
| 网关开始发 `ai.tts.start` | **回滚** |
| 网关不发送被打断那一轮的音频 | **回滚** |
| 客户端 DI 接上会出声的解码器 | **回滚**（解码器本体保留）|

**我不确定是哪一笔导致的静音** —— 两笔同时上、同时表现为「没有声音」，而**没有任何测试看得见「静音」**。这是我的流程错误，下面 §4 讲。

**但有一件事我在回滚时想明白了，而且它是必然的**：`interrupt` 在**每一次** `user.speech.start` 上都会发（日志里每一轮开始都有 `interrupt received`）。而我把「被打断」这个标记用成了「这一轮的音频不发」—— **tap-to-start 模式下，每一轮开始时那个 interrupt 都会把该轮的音频标成不发**。

**所以「被打断的轮次不发音」这条，在 tap-to-start 下必然静音。** 不依赖任何别的东西。这个结论我很有把握 —— 它是从我自己的日志里读出来的，而不是猜的。

---

## 2. 业界有没有这个问题？有，而且是核心问题

**有，而且它是流式语音里最经典的一类问题。** 调研到的共识：

### 打断是**三个**动作，不是一件

| | 做什么 | 谁做 | 为什么不能省 |
|---|---|---|---|
| 1 | **停生成** | 服务端 | 省算力，且让上下文与「用户听到的」对齐 |
| 2 | **停播放** | **客户端，立即，不等服务端** | 见下 |
| 3 | **修状态** | 两边 | 把上下文截断到用户实际听到的部分 |

### 最关键的一条，而且**我们做反了**

> **stop playback client-side the instant barge-in is detected — the server
> round-trip is for context reconciliation, not for stopping audio**

**「停音频」这件事不该由服务端负责。** 服务端那趟往返是用来对齐上下文的，不是用来停止声音的。

**我们反过来了**：我把「停」做在了服务端（不发音频），客户端那半（`interruptNow()`）本来就有但没有作为主机制。

### 业界怎么处理「已经在途的帧」

> expect a few in-flight frames to still arrive. Those should be **discarded**;
> the `onInterrupted` callback **marks the point after which no more frames for
> the cancelled turn will come**

**关键在最后半句**：有一个标记，指出「从这一点起不再有该轮的帧」。**那就是轮次归属。**

### 标杆实现

OpenAI Realtime 是三件套：**`response.cancel`（停生成）+ `output_audio_buffer.clear`（清客户端缓冲）+ `conversation.item.truncate`（把上下文截到听到的位置）**。

### 延迟预算

| 步骤 | P50 |
|---|---|
| VAD 检测 | ~200ms |
| **停 TTS / flush 播放缓冲** | **~50ms** |
| 取消在途 LLM | ~50ms |
| 标记上下文 | ~10ms |
| **合计** | **~310ms** |

**P50 > 350ms / P95 > 600ms，用户会听到两个声音。** 注意第二步只要 50ms —— 因为它是**本地的**。任何走服务端的方案都进不了这个预算。

## 3. 为什么这一次的解法看着不协调

**四条，逐条都能指到具体的东西。**

### 3.1 正确性依赖**一个帧的缺席**

客户端的音频有**两条路**：

```
二进制帧到达 → TTSFrameDispatcher.handle(audio:)
              ├─ 见过 ai.tts.start → 认领（走解码器）
              └─ 没见过           → false → 回落 audioEngine.play(frame:)
```

**哪条路是活的，取决于「服务端有没有发过一个它故意不发的帧」。** 今天音频能出声，正是**因为**那个帧缺席。

**这是根本的不协调**：一条链路的正确性建立在另一条的缺失上。而我做的「把那个帧发出来」——**看起来是修，实际是同时把承载声音的那条路换掉了**。两件事被绑在一起，而我当时把它们讲成了两件。

### 3.2 两条路的**打断语义不同**，而切换它们不改变任何测试

- **fallback**（`audioEngine.play`）：照播，不做轮次判断
- **dispatcher**：`.draining` 之后**认领但不播放**

**同一个「点一下打断」，在切路径前后的行为不一样** —— 而 `swift test` 里没有一条能看见，因为测试绑定的是 `MockTTSDecoder`，它**两条路都不出声**。

### 3.3 「停」被放在了错误的一侧

见 §2：**业界是客户端立即停、服务端停生成**。我做的是**服务端不发**，客户端那半留在原地。**这不是等价的做法，顺序错了。**

为什么我会这么选？因为**信息在服务端**（网关知道打断、知道轮次）。**那恰恰是协议没把信息送到客户端的症状，不是把逻辑放服务端的理由。**

### 3.4 它不可测，而失败模式是**静音**

`EngineBackedTTSDecoder` 有四条测试：顺序、跨轮顺序、codec 校验、空负载。**它们全对，全绿，而真机上一声没有。**

顺序测试证明桥是保序的，**证明不了桥上有没有人**。而我当时把那四条测试当成了「这条路径已经验过」。

## 4. 我的流程错在哪（这才是要记的）

1. **两笔同时上、同时重启。** 真机第一跑就分不清是哪一笔。**「一次只改一处」是我自己写在 P0-2 里的纪律，这次没照做。**
2. **把「有测试」当成了「验过」。** 四条测试覆盖的是顺序与校验，不是「有没有声音」。**静音在单元测试里没有表示。**
3. **回滚本身也踩了同一个坑**：我用脚本按字符串锚点改 `AppDependencies.swift`，锚点在文件里**不唯一**（`XCTestConfigurationFilePath` 出现两次），改错了地方、删掉了一大段。**同一个错误在当晚出现了两次**（另一次是红验证改错了守卫）。**同名锚点不能靠字符串匹配** —— 这条当晚已经写进 backend `docs/65`，现在再记一次，因为我又犯了。

---

## 5. 重新落地应该怎么做

**顺序反过来，一步一验：**

1. **先把客户端那半做对**（**没有服务端依赖**）：打断时客户端**立即** flush，并把「不再播放」做成 `interruptNow()` 的语义 —— 这是业界共识的第 2 步，**今天它已经在了，只是不是主机制**。
2. **真机验**：不打断的一轮有声音；打断的那一轮**立即静**。**此时服务端一行没改。**
3. **再单独上服务端的「不发被打断轮次的音频」** —— 但**先修 §1 那个必然错误**：`interruptedThisTurn` 不能由「轮次开始时那个 interrupt」置位。判据是「这一轮**已经开始产出**之后才被打断」。
4. **最后才谈 `ai.tts.start`** —— 它是给客户端**识别在途帧**的能力，属于第 1 步的增强，**不是停音频的机制**。而且它一次换掉整条音频路径，**必须单独一次真机跑**。

**每一跑之间只改一件事。**

---

## 6. 一句话

> 打断的正确形状是：**客户端立即停（本地、50ms），服务端停生成（省钱、对齐上下文），
> 一个标记让在途的残帧可识别**。
>
> 我做成了：**服务端不发**（跨网络的「停」，慢且错侧）+ 顺手把客户端整条音频路径换掉（不可见的静音风险），**两件绑在一次真机验证里**。
>
> **看着不协调，是因为它确实不协调** —— 不是解法错，是**顺序和分层同时反了两个**。
