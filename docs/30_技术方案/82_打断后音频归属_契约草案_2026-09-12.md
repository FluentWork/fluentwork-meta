# 打断之后，那一条音频该由谁来停 —— 契约草案

**日期**：2026-09-12
**状态**：**草案，未实现。** 需要先定方向，再动任一仓。
**起因**：`77_` **P0-11**（音频要等点击才播 / 打断停不下正在来的音频）
**前置**：ios `9fac40e` —— 复现测试已经建立，它**通过**，通过就是复现

## 1. 现象，以及它的数字

用户场景：让 AI 长回答 → TTS(A) 播放中 → 立即点「开始说话」并说话 → 右侧显示
「正在转写」，但**A 还在播**；A 播完后，左边的内容其实已经翻到下一轮了。

真机日志（`log_id 202609120357474A5842DF6B868DC8AC4F`）：

| 事实 | 数值 |
|---|---|
| turn-1 的 `ai.tts.end` | **`duration_ms: 61232`** —— 厂商为这条回复花了 **61 秒** |
| 它的 **113 帧**（`sequence` 500…612）到达客户端 | **1.1 秒内全部**（`total_ms` 17327 → 18430）|
| 于是 | 头 ~60 秒里，回复**已存在、未送达**；用户的手**点在这个窗口里** |

打断因此发生在**它要打断的音频到达之前**。

## 2. 为什么现在的契约表达不了这件事

客户端的门禁（`AudioPlaybackGate`）是**序号水位线**：

```swift
mutating func markInterrupted() -> UInt32? {
    interruptWatermark = lastAcceptedSequence   // 已经收到过的最大序号
}
mutating func shouldAccept(_ frame) -> Bool {
    if let w = interruptWatermark, frame.sequence <= w { return false }
    ...
}
```

水位线记的是**已经见过的编号**。**还没送达的帧编号更大**，所以一帧都拦不住 ——
上表那 113 帧全部 `> 499`，**全部被接受**。这不是实现 bug，是**契约里没有信息**：

> **二进制音频帧上只有序号，没有轮次归属。**

`provider.go` 里那条注释（`SequencedVoiceProviderSession`）已经写明这个前提。
序号能表达「新旧」，表达不了「属于谁」。

## 3. 两个方向，代价差很多

### 方向 A（我最初想的）：帧上带轮次归属

在二进制头里加一个轮次序号，或每轮开头补一个控制帧。客户端据此丢弃「被打断那
一轮」的剩余帧。

**代价**：
- 动二进制帧格式 = **两个仓必须同时上线**，版本错配会**整条音频失效**；
- 或者补发 `ai.tts.start` —— 而**今天刻意不发它**是有原因的
  （`provider_volc_duplex.go:808` 起）：`TTSFrameDispatcher` 见到 start 才认领
  二进制帧，而绑进它的解码器**不驱动 AVAudioEngine**，一发就把音频挪到不出声
  的那条路上。**发它等于同时要修客户端的解码路径。**

### 方向 B（推荐）：**网关不发送客户端已经不要了的音频**

**这件事全部的信息都在服务端。** 网关**已经知道**用户打断了 —— 后端日志里每
次点击都有两行：

```
"interrupt received"                                  component=voicegateway.handler
"interrupt forwarded to live provider boundary"       component=voicegateway.provider.volc_duplex
```

它只是**没有据此做任何事**：被打断那一轮的音频照样在 `collectTurn` 收尾时
整批发出去。

**改法**：网关记住「哪一轮被打断了」，在该轮音频出站前跳过它。

**为什么它比 A 好，四条都独立成立**：

| | |
|---|---|
| **零协议改动** | 不加字段、不改二进制头、不需要两仓同步上线 |
| **信息本来就全在服务端** | 轮次归属、打断事件、出站决策，三样都在网关手里 |
| **省带宽** | 61 秒的音频根本不发，而不是发过去再丢掉 |
| **不需要「客户端识别轮次」这个能力** | 客户端不必知道帧属于谁，它只要没收到就没收到 |

**它同时也解释了 P0-11 的另一半**：如果一条 61 秒的回复被整批推迟发送，那么
「音频要等用户点一下才播」和「打断停不下」很可能是**同一个根因**的两张脸 ——
音频的**出站时机**由 `collectTurn` 收尾决定，而不是由它产生的时刻决定。

## 4. 方向 B 要定的三件事

1. **「被打断」的判定**：现在 `interrupt` 落到 provider 边界，由 provider 处理。
   要把它提升成 `sessionRuntime` 上的一个**轮次标记**（`interruptedTurnID`），
   出站路径读它。**谁来清**：下一轮开始时清，而不是打断自己清 —— 同一轮可能被
   打断多次。
2. **已经在途的帧**：网关发出去的帧拦不回来。所以**客户端侧仍要保留
   `interruptNow()`**，方向 B 与它不是二选一，是两层。
3. **`interrupt forwarded ... delivered_chars: 0` 这个 `0`**：日志里每次都是 0。
   它意味着打断**没有把已生成内容交给 provider 去「收回」**。这条要不要一起看？

## 5. 验证

**可先做的（不需要真机）**：`sequence` 与「该轮是否被打断」的判定是纯逻辑，
后端可以单测：构造一轮被打断 → 断言该轮的音频一帧都不进 outbound。

**真机判据**（沿用 P0-11 的场景）：
1. 让 AI 长回答，播放中打断并说话；
2. **期望**：A **立即静音**，而不是播完；
3. 后端日志应出现「跳过被打断轮次的音频」一行，带 `turn_id` 与跳过的帧数；
4. **反面对照**：不打断的一轮，音频一帧不少。

## 6. 本草案**不**解决的

| | |
|---|---|
| 客户端**已经收到并排进队列**的帧 | 属于 `interruptNow()` 的职责，已在（`LiveAudioEngine.swift:735`）|
| `ai.tts.start` 缺失导致「音频 20 秒只到 2 帧」类问题 | 见 `77_` P0-11 的排查记录 —— **另一个方向** |
| 空会话灌满列表 | `77_` P0-13 |
| 回顾兜底 | `77_` P0-15 / `81_` |
