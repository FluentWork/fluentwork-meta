# I20 收口与全链路架构设计文档

**版本**：V1.0　**日期**：2026-09-03　**状态**：规划中

---

## 一、问题背景

### 1.1 I20 遗留问题清单

根据 `docs/20_I20_voice_turn_boundary_pitfalls.md` 的分析，当前生产路径有 **4 个独立缺陷叠加**，在 60s 超时场景下表现为：

1. **`collectTurn` 超时报 `outcome=ok`**：`collectTurn` 在 60s 超时后没有显式标记 `outcome=timeout`，以 `outcome=ok` 返回，导致 transcript=0、assistant_text=0 但系统认为正常
2. **iOS WS 端继续发送音频帧**：60s 超时触发后，iOS 的 `LiveAudioEngine` 没有停止发送 binary 音频帧，继续倒进 backend 的 `handleAudio`，触发 80+ 条重复 WARN
3. **`HandleClientAudio` 失败时继续尝试写 iOS WS**：每次写都报 `use of closed network connection`，80 次 WARN 级联
4. **Warn 日志无去重**：60s 内 80 条相同 WARN 是纯噪声，掩盖真实错误

### 1.2 架构现状

项目是 **iOS + Go Backend 双仓库**：

```
┌─────────────────────────────────────────────────────────────┐
│ fluentwork-ios (Swift/iOS)                                  │
│  ├─ FluentWorkCore (状态机/AudioEngine/网络)                 │
│  ├─ FluentWorkNetworking (WebSocket/音频帧)                 │
│  ├─ FluentWorkUI (SwiftUI 视图)                             │
│  └─ FluentWorkDiagnostics (Tracker/Logging)                 │
└──────────────────────────┬──────────────────────────────────┘
                           │ WSS (WebSocket)
┌──────────────────────────▼──────────────────────────────────┐
│ fluentwork-backend (Go)                                      │
│  ├─ voicegateway (WSS Handler + Provider 接口)              │
│  ├─ voicepoc (Volcengine Duplex 调用封装)                   │
│  └─ internal/* (业务模块)                                    │
└─────────────────────────────────────────────────────────────┘
```

## 二、实现计划

### 2.1 P0：Turn 超时显式 `outcome=timeout`

#### Backend 侧

**当前状态**：`volc_duplex.go` 的 `collectTurn` 已有 B15 变更，`TurnOutcomeTimeout` / `TurnOutcomePartial` / `TurnOutcomeOK` 三值已定义，超时路径也已处理。

**待完成**：`provider_volc_duplex.go` 的 `HandleClientControl` 在调用 `WaitTurnResult` 时，需要把 `TurnResult.Outcome` 透传到 `turnToOutbound`，并在 outcome 为 `timeout` 时主动发送 `ai.turn.end` 让 iOS 状态机能够离开 `.processing`。

**关键文件**：
- `internal/voicepoc/volc_duplex.go` - `collectTurn` 已有 `outcome=timeout`（✅ B15 已完成）
- `internal/voicegateway/provider_volc_duplex.go` - 需要透传 `outcome`，在 `timeout` 时也发 `ai.turn.end`

#### iOS 侧

**当前状态**：`SpeechSessionMiddleware` 在收到 `ai.turn.end` 时触发 `.aiTurnEnd` 事件驱动状态机。

**待完成**：在 `SpeechSessionMiddleware` 的 `transportEvents` 循环中，为 `.processing` 状态增加一个客户端侧超时兜底：当进入 `.processing` 超过 70s（如 60s + 10s buffer）仍未收到 `ai.turn.end`，主动触发 `vadSpeechEnd` + `session_end` 兜底逻辑，不再依赖 backend 的 outcome。

**关键文件**：
- `Shared/FluentWorkCore/Architecture/Middleware/SpeechSessionMiddleware.swift`
- `Shared/FluentWorkCore/SpeechSession/SpeechSessionMachine.swift`

#### 重点难点

- **难点**：iOS 超时兜底需要在 middleware 层引入 timer，且必须在 `.processing` 状态时启动，`ai.turn.end` 到达时取消
- **重点**：兜底触发后仍需向 backend 发送 `session.end`，避免留下僵尸 session
- **测试**：需要用 `InMemorySocketTransport` mock 验证 iOS 在收到 `ai.turn.end` 后超时兜底不触发

### 2.2 P0：iOS 超时兜底（停止发送音频）

#### 当前状态

iOS `LiveAudioEngine` 的 `SpeechSessionMiddleware` 监听音频事件：`speechEnded` → `sendSpeechBoundary(started: false)` → backend `HandleClientControl`。

**问题**：当 `collectTurn` 超时（60s），iOS 仍继续发送音频帧（因为 VAD 还在活跃），导致 backend `handleAudio` 继续被调用。

#### 实现方案

在 `SpeechSessionMiddleware` 中引入 Turn 级别超时：

1. `vadSpeechEnd` 触发时（用户结束说话），记录 `turnStartTime`
2. 在 middleware 中启动一个 `.task` 跟踪当前 turn 的处理时间
3. 70s 后（`defaultVolcTurnWait=60s + 10s buffer`）仍未收到 `ai.turn.end`，则：
   - 取消 `transportEvents` 中的 `transportEvents` task（不再处理后续音频帧）
   - 触发 `.endSession` 效果
   - 不再发送 `binary` 音频帧到 backend
   - 可选：发送 `session.end(reason: "turn_timeout")`

**关键文件**：
- `Shared/FluentWorkCore/Architecture/Middleware/SpeechSessionMiddleware.swift`
- `Shared/FluentWorkCore/Services/LiveAudioEngine.swift`

#### 重点难点

- **并发安全**：`turnStartTime` 需跨 task 共享，使用已有的 `TurnCountBox` 类似模式
- **取消传播**：取消 `transportEvents` task 后，iOS 不再处理任何来自 backend 的帧，但 WSS 连接本身不关闭（允许 reconnect）
- **避免竞争**：取消操作需幂等，防止重复取消导致 panic

### 2.3 P1：Backend `handleAudio` 写失败立即退 session

#### 当前状态

`handler.go` 已有 `rt.broken = true` 的 B15 变更：当 `HandleClientAudio` 失败时，设置 `rt.broken = true` 并返回 error 帧给 iOS，后续 binary 帧直接 drop。

**问题**：`handleAudio` 返回后，loop 中的 `continue` 继续下一次迭代，下一次 `conn.Read` 可能成功（如果 iOS 还在发），导致继续调用 `handleAudio`。

#### 实现方案

`handler.go` 的 B15 变更已正确实现：
- `rt.broken = true` 后，`handleAudio` 直接 return `nil`（不在调用 writeJSON）
- loop 继续迭代，但下一次 binary 帧进入时，`handleAudio` 开头检查 `rt.broken` 直接 return
- 最终 iOS 关闭 WS 或下一次 read 超时，loop 退出

**验证点**：
1. `rt.broken` 设置后，后续 binary 帧不再调用 `HandleClientAudio`
2. 返回 `nil` 而非 error，让 loop 继续（等待 WS read 失败或 iOS 关闭）
3. iOS 收到 `provider_audio_failed` error 帧后，触发 `networkLost` → reconnect 窗口

#### 重点难点

- **重启 reopen 逻辑**：`reopenAttempted` 只重试一次，防止无限循环
- **Error 帧只发一次**：B15 已处理（通过 `rt.broken` guard），验证即可

### 2.4 P1：Warn 日志去重

#### 当前状态

`handler.go` 中 `HandleClientAudio` 每次失败都打 `WARN "provider audio forward failed"`，60s 超时场景下产生 80+ 条相同日志。

#### 实现方案

在 `handler.go` 的 `sessionRuntime` 中增加 warn 去重逻辑：

```go
type sessionRuntime struct {
    // ... existing fields ...
    // B15: warn deduplication
    lastWarnKey   string
    lastWarnAt    time.Time
    warnCount     int
}

const warnDedupeWindow = 5 * time.Second

func (h *Handler) logWarn(key string, msg string, args ...any) {
    now := h.now()
    if key == rt.lastWarnKey && now.Sub(rt.lastWarnAt) < warnDedupeWindow {
        rt.warnCount++
        // 每 N 条只打一条
        if rt.warnCount%10 == 0 {
            h.logger.Warn(fmt.Sprintf("%s (deduped %d times)", msg, rt.warnCount), args...)
        }
        return
    }
    rt.lastWarnKey = key
    rt.lastWarnAt = now
    rt.warnCount = 1
    h.logger.Warn(msg, args...)
}
```

**采样策略**：相同 warn 在 5s 窗口内只打第一条，第 10/20/30... 次时打一次带计数摘要。

#### 重点难点

- **Key 构造**：warn key 应包含足够上下文（如 `err.Error()` 内容），但不要太长
- **不过度去重**：真正的错误仍需可见，只是避免 80 条完全相同的噪声

### 2.5 T2：dev-echo provider + 预录 PCM fixture 本地复现

#### 现状

`provider_dev_echo.go` 已实现 dev-only provider：
- 忽略真实音频
- `user.speech.end` 返回配置的 echo text 作为 ServerASRText
- 不需要 Volcengine 凭证

**缺失**：没有预录 PCM fixture 的支持，iOS 真机问题（如 VAD silenceHold 太短）无法在本地复现。

#### 实现方案

**Backend 侧**：
1. 扩展 `DevEchoVoiceProvider` 支持从文件加载预录 PCM
2. `VOICE_DEV_ECHO_FIXTURE=/path/to/fixture.pcm` 环境变量指定 fixture
3. `HandleClientAudio` 读取 PCM 文件，每次调用返回下一个 20ms chunk
4. 支持 `turn_id` 对应的独立 fixture 文件（`/fixtures/turn-{n}.pcm`）

**iOS 侧**：
1. 在 `InMemorySocketTransport` 中增加 fixture 模式：接收 `binary` 帧时记录
2. 同时在测试中添加 `FixtureAudioEngine`：从 fixture 文件读取 PCM，模拟真实 VAD 触发序列
3. 在 `LiveAudioEngineTests` 中用预录 fixture 测试 `silenceHold=350ms` vs `1500ms` 的差异

**关键文件**：
- `internal/voicegateway/provider_dev_echo.go` - 扩展支持 PCM fixture
- `Tests/FluentWorkCoreTests/Audio/LiveAudioEngineTests.swift` - 添加 fixture 测试
- `Shared/FluentWorkNetworking/Socket/InMemorySocketTransport.swift` - 增加 fixture 录制模式

#### 重点难点

- **Fixture 管理**：预录 PCM fixture 的格式（必须是 16kHz mono PCM16）和命名规范
- **真实 VAD 场景**：fixture 场景下 VAD 触发点必须和真实场景一致，否则 fixture 无意义
- **与 mock 的区别**：dev-echo 是 **end-to-end** 测试（iOS → backend → iOS），不是 mock；fixture 是 **音频输入** 替换

### 2.6 T3：全链路 trace 对齐

#### 现状

当前 trace 链路中存在多种 ID：

| ID | 位置 | 用途 |
|---|---|---|
| `session_id` | iOS ↔ Backend ↔ Volcengine | 端到端 session 标识 |
| `turn_id` | iOS → Backend | 用户 turn 编号（`turn-1`, `turn-2`） |
| `log_id` | Backend → Volcengine | Volcengine 日志追踪 |
| `trace_id` | 埋点事件 | 可观测性平台关联 |

**问题**：各层日志中的 ID 分散，难以串成完整时间线。例如：
- iOS 日志：`turn_ended turn-1, session_id: s-123`
- Backend 日志：`turn result captured, active_turn_id: volc-turn-1, session_id: s-123`
- Volcengine 日志：`log_id: volc-log-456`（iOS 和 backend 日志中没有关联）

#### 实现方案

**统一 trace context 传播**：

```
iOS (生成) → Backend (接收) → Volcengine (使用)
   session_id      session_id       session_id
   turn_id         turn_id         (Volcengine 无 turn_id 概念)
                    log_id ← Volcengine 返回时关联
```

1. **iOS 侧**：
   - 在 `SpeechSessionMiddleware` 中，每次 `vadSpeechEnd` 时同时记录 `turnID` + 对应的服务端 `log_id`（如果收到）
   - `SpeechSessionTimingsRecorder` 中增加 `logID` 字段
   - Tracker 事件中同时携带 `session_id` + `turn_id`

2. **Backend 侧**：
   - `handler.go` 的 `loop` 在处理每个帧时，把 `session.SessionID` 和当前的 `log_id`（从 provider 获取）写入 log context
   - `volc_duplex.go` 的 `OpenDuplex` 返回 `logID`，在 `sessionRuntime` 中保存
   - 所有 `h.logger.Info/Warn` 加上 `log_id` 属性

3. **iOS logging 增强**：
   - `OSLogLogger` 中增加 `trace_id` 字段（类似 `session_id` 的传递）
   - 在 `SpeechSessionMiddleware` 初始化时生成 `trace_id`，在所有 tracker 事件中携带

**关键文件**：
- `Shared/FluentWorkCore/SpeechSession/SpeechSessionTimingsRecorder.swift` - 增加 logID
- `Shared/FluentWorkDiagnostics/Logging.swift` - 增加 trace context
- `internal/voicegateway/handler.go` - log_id 贯穿
- `internal/voicepoc/volc_duplex.go` - log_id 返回

#### 重点难点

- **向后兼容**：不能破坏现有日志格式，新增字段可选
- **Volcengine log_id 关联**：Volcengine 返回 `X-Tt-Logid` 在 `OpenDuplex` 时记录，需在 backend 响应处理中关联到 iOS 的 `turn_id`

### 2.7 T4：手动触发 VAD 降级为可选

#### 现状

`LiveAudioEngine` 中的 `AudioSpeechActivityTracker` 使用自动 VAD（能量检测 + silenceHold）判断用户说话结束。PRD 本来就写了"按住说话/点击说话"模式，但当前实现以自动 VAD 为主。

#### 实现方案

**双模式架构**：

1. **主模式：按住说话（Manual PTT）**
   - 用户按住按钮 → `holdStart` → `vadSpeechStart`（不等 VAD）
   - 用户松开按钮 → `holdEnd` → `vadSpeechEnd`（不等 VAD）
   - 音频在按住期间持续发送

2. **降级模式：自动 VAD（可选，默认关闭）**
   - `AudioSpeechActivityTracker` 在 `silenceHold` 后触发 `.speechEnded`
   - 可通过 FeatureFlag 开启（`feature_auto_vad_enabled`）

**iOS 侧实现**：
```swift
// SpeechSessionMiddleware.audioEngineEvents
case let .buttonState(isPressed):
    if isPressed {
        // Manual PTT mode (primary)
        try await speechClient.sendSpeechBoundary(started: true, turnID: nil, text: nil)
        await dispatchBox.dispatch(.speakingRoom(.session(.holdStart)))
    } else {
        // Manual release - end turn without waiting for VAD
        try await speechClient.sendSpeechBoundary(started: false, turnID: turnID, text: nil)
        await dispatchBox.dispatch(.speakingRoom(.session(.holdEnd(turnID: turnID))))
    }
```

**UI 层**：
- SpeakingRoomView 中，说话按钮改为按住说话按钮（`LongPressGesture`）
- 按住期间显示录音状态，松开触发 `holdEnd`
- 自动 VAD 作为 FeatureFlag 可选项

**关键文件**：
- `Shared/FluentWorkCore/Services/LiveAudioEngine.swift` - VAD tracker 保持不变（降级用）
- `Shared/FluentWorkCore/Architecture/Middleware/SpeechSessionMiddleware.swift` - 增加 `.holdStart` / `.holdEnd` 处理
- `Shared/FluentWorkUI/SpeakingRoom/SpeakingRoomView.swift` - 按钮交互

#### 重点难点

- **两种模式的平滑切换**：自动 VAD 和手动 PTT 产生的 `vadSpeechStart/End` vs `holdStart/End` 事件需要被状态机统一处理
- **按住说话的防抖**：用户快速按下松开（<100ms）不应触发 turn
- **PRD 一致性**：确保 UI 文案和技术实现与 PRD 的"按住说话/点击说话"描述对齐

## 三、架构重点与难点总结

### 3.1 跨仓协调点

| 变更点 | iOS | Backend | 需要同步 |
|---|---|---|---|
| 超时兜底逻辑 | ✅ 新增 middleware timer | ✅ `outcome=timeout` 透传 | ✅ 协商 timeout duration（70s） |
| session 异常退出 | ✅ 收到 `provider_audio_failed` | ✅ `rt.broken` + error 帧 | ✅ 确认 error code |
| trace ID 对齐 | ✅ Tracker 事件增加 log_id | ✅ logger context 增加 log_id | ✅ schema 对齐 |

### 3.2 关键风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| iOS 超时 timer 和 backend `ai.turn.end` 竞争 | 两边都触发 session.end，导致重复操作 | 幂等设计 + backend session 幂等关闭 |
| dev-echo fixture 和真实 VAD 差异 | fixture 测试通过但真机失败 | fixture 用真实采集数据 + 与 smoke test 对照 |
| 自动 VAD 和手动 PTT 模式混淆 | 用户感知不一致 | FeatureFlag 明确标注，默认关闭 |

### 3.3 测试策略

| 层级 | 工具 | 覆盖范围 |
|---|---|---|
| iOS 单测 | `InMemorySocketTransport` + `LiveAudioEngineTests` | 状态机、middleware 副作用、超时 timer |
| Backend 单测 | `handler_b15_test.go` + `volc_duplex` 测试 | `outcome=timeout` 透传、warn 去重、rt.broken |
| E2E 本地 | dev-echo provider + 预录 PCM fixture | 真实 WSS 帧流、完整 turn 生命周期 |
| E2E 真机 | smoke runbook (`smoke-iphone17pro.sh`) | 蓝牙 AEC、打断体感、弱网降级 |
