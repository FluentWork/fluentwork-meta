# FluentWork 语音链路架构评价

**版本**：V1.0  
**日期**：2026-09-10  
**定位**：在**理解这个系统想做什么**的前提下，评价它现在的结构。不是 bug 清单（那些在 `fluentwork-backend/docs/42–48`），是结构与产品意图的匹配度。  
**锚点**：`fluentwork-ios` `dc5d520` · `fluentwork-backend` `3e1efed`  
**配套**：[`52_架构图`](./52_语音链路架构图_2026-09-10.md) · [`74_SDK 调研`](../70_外部研究/74_语音实现方式再评估_2026-09-10.md)

## 0. 先说清楚这个系统想做什么

评价之前必须把判据钉死。从 PRD（`20_产品设计/20`、`22`）与 `80_项目整体蓝图`提炼：

**它不是一个语音助手。语音只是输入方式。**

产品的产物在**对话之后**：

```
说  →  命中（哪个短语可以更地道）  →  炼化（更地道的表达）
 │                                          │
 └──────────  语料库增长  ←── 复习 / 每日一读
```

对应 PRD 里那条「用户带走的产出」。`72_` 说得最直接：**「FluentWork 的差异化在'对话之后'」**。

**所以判据是**：这套结构，是否把"每话轮的文本 + 轮次元数据"**完整、可靠、可观测**地送到了服务端，让"对话之后"那一半能成立？

不是"能不能对话"。对话是前提，不是目标。

## 1. 做对的地方（先说这个，因为确实做得好）

### 1.1 零 key 是硬约束，而且做成了

**iOS 里搜不到任何第三方凭证**（`53_测试与验收/53` §2.5 把它列成验收项）。凭证只驻服务端，客户端只连自研网关。

这在移动端产品里是**少见的克制**——大多数团队会图快让客户端直连。这条纪律保护的是：换供应商只改网关、凭证不随 App 分发、能对供应商侧的每一帧做观测。

### 1.2 Provider 防腐层是真的防腐

`VoiceProvider` 接口 + `Mock` / `DevEcho` / `VolcDuplex` 三个实现。**供应商类型不外溢**（`51_测试与验收/51` §5.5 把它列为门禁）。这一晚能用一个 `DevEcho` provider 把整条链路在本地跑通、能用 mock WSS 复现真机 bug，都是这层的红利。

### 1.3 纯状态机 + 中间件解释副作用

`SpeechSessionMachine` 零 IO，13 相全部可单测。所以「60s abort 不是 B15」这种**语义分叉能被钉成测试**，而不是靠文档口口相传。

跨端不变量（`turn_id` = `turn-N`、`outcome` 枚举、v1 字节冻结）都有跨仓 fixture 对账。

### 1.4 契约治理做到了很少见的程度

schema 真源在 `fluentwork-infra`，两仓镜像，v1 用 SHA-256 钉死字节。跨仓协议能治到这个粒度，是这套仓群**最扎实的一块**。

## 2. 结构性错配

以下四条不是"哪里写错了"，是**结构本身与产品意图的错位**。前两条我建议优先处理。

### 2.1 ⚠️ 「AI 不会说话」被归因错了地方

**文档的归因**（`66_` §6、`51_技术方案/51` §8）：I15 真机流式 Opus TTS 阻塞，原因是**火山 Opus SDK `not-available`**，客户端仍是 mock decoder。措辞暗示"服务端有音频，客户端解不了"。

**代码的事实**：`provider_volc_duplex.go` 的出站集**只有** `client.asr.transcription` / `ai.turn.end` / `ai.text.delta` —— **没有任何 `ai.tts.*`，没有二进制帧**。厂商推的 `response.output_audio.delta` 被 `collectTurn` 读完即丢（只用来判 `seenResponse`）。

**客户端侧独立坐实**：2026-09-10 两次真机会话的 `transport_rx` 里出现过 `session.ready` / `client.asr.transcription` / `ai.turn.end` / `ai.text.delta` / `pong` / `error`，**从未出现过 `ai.tts.start`**。

**已与负责人确认**：真机上确实没有 AI 声音，TTS 播放（解码 + 说话）尚未开工。所以这不是回归 —— 是**尚未实现的能力**。

**后果（这一条是省时间的提醒）**：文档把 I15 的阻塞归因为**客户端缺 Opus 解码器**（「火山 Opus SDK `not-available`，客户端仍是 mock decoder」）—— 措辞暗示"服务端有音频，客户端解不了"。**但服务端根本没有转发音频。** 如果下一步按文档去做解码器，会发现**没有音频可解**。

真正要动的是**网关**：把厂商已经推下来的 `response.output_audio.delta` 转出去。这一步零新增供应商、零新增成本。**但见 §2.5 —— 转出去也不会是"流式"的。**

**为什么这是结构问题而不是 bug**：`73_` 拍板「4 个音色属于独立流式 TTS（`seed-tts-2.0`），不是 duplex 内置」——所以**丢弃 duplex 内置音频是设计决定**（音色不可控）。但替代方案（B17）没有接上（见 2.2）。于是设计上"应该有声音"、实现上"两条路都没通"，而文档把账记在了客户端解码器上。

### 2.2 ⚠️ B17 TTS：造好了，没有消费者

`internal/content/tts` 是一份**完整实现**：流式 provider + duplex 降级 + 连续 3 次 5xx 熔断 + Prometheus 指标 + HTTP 端点。

**零调用方。** 全仓只有 `cmd/app-server/main.go:132` 引用了它（构造 handler）。`POST /internal/v1/tts/synthesize` 是 internal-token 保护的，iOS 调不到；网关在说房间的 turn 里也不调它。

**后果**：一段真实投入闲置，而说的房间因此完全没有 AI 语音。

**这条和 2.1 是同一个洞的两面**——所以修的时候要一起决定：说的房间的 AI 声音，到底走哪条路？

### 2.3 最贵的一段没有成本记账

全仓核实：`internal/voicegateway`、`internal/voicepoc`、`internal/content/tts` **没有任何 `ai_cost_logs` 写入**。

`ai_cost_logs` 只记 Ark 的 review/refine。也就是说：

- **按分钟计费的 duplex**（ASR + LLM）
- **按字符计费的 TTS**

——这两项**在成本账上是隐形的**。而它们大概率是可变成本的主体（对话比一次 review 贵得多）。

**后果**：无法定价、无法做成本熔断、账单异常时无法归因到用户/会话。`51_技术方案/51` §9 把「成本熔断」列为"有 cost log，无自动熔断"——但实际情况更靠前：**语音这条根本没有 log**。

### 2.4 状态机的复杂度超过了产品语义

13 个相位、6 个 timer（60s abort / 70s B15 / 15+45+30s 子阶段 / 20s 评价）。而产品形态是**「说一句，听一句」**。

这一晚修掉的 4 个真机缺陷里，**3 个出在这个区域**：
- 录音轮次外的 PCM 上行（CaptureGate 语义）
- abort 落点的相位错误
- 每轮失忆（reopen 预算 × 读上限）

再加上"三条等太久不能合并"那条反复被误判的合同。

**这不是写得差** —— 恰恰相反，13 相每一个都有测试。问题是**相位数量成了复杂度的来源本身**：每加一相，就意味着多一组 `(相位, 事件)` 组合要证明其合法性，而产品只需要区分"该谁说"。

> 一个具体的观察：`waitingForAIAnswer` 和 `waitingForEvaluation` 是**两个不同的相位**，但产品上都是"等对方"；`processingASR/LLM/Review` 三相都只是"在处理"。**相位在承载实现细节，而不是产品语义。**

### 2.5 「流式」没有流到客户端

**订阅了流式的供应商事件，却以批量的方式交付给客户端。**

`turnToOutbound` 构造 `ai.text.delta` 用的是 `turn.AssistantText` —— **整轮累积完的全文**；而 `collectTurn` 是「读完整轮才返回 `TurnResult`」，没有任何增量回调。所以真实时序是：

```
用户说完 → 网关一直读供应商事件（全憋着）
        → response.done 到达
        → 一次性 flush：client.asr.transcription + ai.turn.end + ai.text.delta(全文)
```

**日志可自证**：`ai.turn.end(partial)` **先于** `ai.text.delta`。不是巧合，是 append 顺序 —— iOS 已经进 `waitingForEvaluation` 了，AI 的文字才到。

**三个后果**：

1. **回合时间线上 AI 的回复整块蹦出**，不是逐字流。PRD 里"AI 文本增量聚合成一条"的设计，拿到的是**一次性的整条**。
2. **即使现在转发音频，也会堆在轮末一次性到达** —— 用户听到"AI 沉默两秒，然后一口气说完"。比没有声音好，但仍不是对话。
3. 要让音频有流式感，`collectTurn` 必须能**边读边发**。那是一个比"转一个字段"大得多的改动。

**这不是 bug —— 是"批量"和"流式"两种架构选择的差异**，而现状尴尬地卡在中间。

### 2.6 两个还没机会暴露、但一出声就会撞上的风险

**① AEC 从未被考验过。** 现在 AI 没有声音，所以回声消除是死的。一旦出声，AEC 立刻进关键路径 —— 否则 AI 会听到自己。**而裸 WebSocket 方案不提供 AEC**（官方协议文档无任何 AEC 字段），只能依赖 Apple `.voiceChat` 的系统 Voice-Processing。实现里方向是对的（`.playAndRecord` + `.voiceChat`），但**从未在"有 AI 声音"的条件下验证过**。

**② 轮次之间不发音频，可能需要显式静音事件。** 官方原文：「客户端关闭麦克风后若不再发送音频帧，须主动发送静音事件 `input_audio_mute.commit`……**否则服务端会因持续收不到音频输入触发超时**」。而 `docs/40`（iOS 停止轮次外 PCM）之后，客户端在两轮之间**确实什么都不发**。真机实测暂时没炸，但**那是"没炸"不是"正确"**。

（两条均见 [`74_`](../70_外部研究/74_语音实现方式再评估_2026-09-10.md) §3.2/§3.3）

## 3. 与 SDK 选型的关系

[`74_`](../70_外部研究/74_语音实现方式再评估_2026-09-10.md) 的结论：**选型已经拍完且闭合**（`71_`/`72_`/`73_` 三份文档 + `62_I15` 架构澄清），全链路自研 relay，不接任何官方客户端 SDK，零 key 是硬约束。

**这个决定我认同**，理由 `72_` 讲得比我能讲的更好：官方 SDK 覆盖的是"对话体验组件"，而 FluentWork 的差异化在"对话之后"；换 SDK 会带走服务端的第一手音频/事件/置信度。

**但决定正确 ≠ 代价为零。** 不接 SDK 意味着下面这些**全部自己负责**：

| 自建 relay 的固有责任 | 这一晚的实例 |
|---|---|
| 传输层的边界条件 | 两个 32 KiB 读上限（`backend/docs/47`、`48`） |
| 重连与恢复语义 | reopen-once 预算、abort 后重建 duplex、每轮失忆 |
| 编码/解码 | Opus 解码器是 `not-available` 桩 |
| 背压与保活 | `sendSilence` 每 20ms 写、keepalive probe、三层 ping |
| 可观测性 | 成本账缺失（见 2.3） |

**这些都是官方 SDK 会替你做的事。** 结论不是"应该接 SDK"，而是：**既然选了自建，就要给这一层留出预算和人力** —— 这一晚的四个 bug 全部出自这一层，不是偶然。

## 4. 建议（按优先级）

| # | 动作 | 为什么现在做 |
|---|---|---|
| **1** | **让 AI 先出声** —— 网关把厂商已推下来的 `response.output_audio.delta` 转给 iOS | 已确认是"尚未实现"而非"阻塞"。零新增供应商、零新增成本。**别再去做客户端解码器** —— 现在没有音频可解 |
| **2** | **同一动作里验 AEC** | AI 一出声 AEC 才是活的（2.6①）。拆成两步会重复劳动 |
| **3** | **给语音链路加成本记账** | 不做就永远拿不到真实占比，也就无法判断该不该迁架构（2.3） |
| **4** | **拿 30 条中式口音英语样本测 ASR 的 WER** | P0 指标。**拆不拆流水线应该由这个数字决定**（见 `74_` §2） |
| **5** | 补 `input_audio_mute.commit` | 消除一个"没炸但不正确"（2.6②） |
| **6** | **B17 要么接上，要么标记为未启用** | 闲置代码会被误读成"已完成的能力" |
| **7** | 把「相位数量」当技术债登记，而不是继续加相 | 见 2.4；下一次改 turn 边界前先评估能否合并相位 |

**明确不要现在做的**：把端到端 duplex 换成分解流水线。选型方向我认同（`74_` §2/§3.4），但**基线不存在** —— 连"AI 出声"都没有的时候换架构，等于同时改两个变量，之后的问题分不清来源。

**不建议做的**：现在切换 SDK。选型论证充分，且切换会同时失去观测面 —— 在真机基线还没建立的时候切换，等于把两个变量一起改。

---

## 5. 一句话

**这套架构的治理水平明显高于它的产品闭环完成度。** 契约冻结、Provider 防腐、零 key、跨仓 fixture —— 这些是很多成熟团队都没做到的；但产品主循环（说→命中→炼化→回顾）最关键的两件事——**AI 出不出声**、**成本可不可见**——目前都还没答案，而且第一件还被归因到了错误的地方。

先补产品闭环，再谈结构优化。
