## ① 本篇回答什么

**三个问题**：

1. 语音对话里「用户在 AI 说话时开口」，业界把它当成什么问题？
2. 标杆实现拆成几步？哪一步必须在端上，哪一步可以异步？
3. FluentWork 原来的代码不是「少写一个 if」，而是缺了哪几条不变量，所以看起来改动面很大？

**读完后你能**：拿着 OpenAI Realtime / LiveKit / 电话 IVR 的做法，对照本项目 9/12 之前的每一处空，说出「缺的是原理还是产品取舍」。

## ② 这是不是个别项目的怪病

不是。它是**流式语音对话的核心问题**，有一个比「打断」更准确的名字：

> **生成时钟、传输时钟、播放时钟三者在长回复上会散开。用户动作落在播放时钟上，协议动作如果落在另外两个时钟上，轮次就会接错。**

只要同时满足下面三条，就一定会出现 95 那种形状：

1. 助手音频是**流式生成、客户端缓冲播放**（先到的帧要排几秒到十几秒）
2. 协议用一个「轮次结束」帧驱动 UI / 状态机（本项目是 `ai.turn.end`）
3. 用户被允许在播放未完成时开口（barge-in）

电话 IVR、车载助手、会议陪同、Realtime API 都满足这三条。区别只在：有没有把「停播放 / 停转发 / 修上下文」写成三个动作，还是合成了一个「发 interrupt 就好」。

本项目 9/11 的 87 把第三步写成「服务端什么都不做」。那不是疏忽文档，是当时代码的诚实描述。它论证对了一半：**停喇叭必须本地、必须不等往返**。它把另外一半（服务端也要知道、记录要对、转发要停）一起省略了。90 已经点名这是偏颇；9/12 补的是那一半，不是推翻「本地先停」。

## ③ 业界把打断拆成三件事

[84 复盘](84_打断这件事为什么看着别扭_复盘_2026-09-12.md) 里写过这张表，这里把它升成原理，而不是一次回滚的附言。

| # | 动作 | 谁做 | 延迟预算 | 省略的后果 |
|---|---|---|---|---|
| 1 | **停播放** | 客户端，立刻 | P50 ~50ms（清缓冲） | 两个声音叠在一起。P50 合计超过 ~350ms / P95 超过 ~600ms，用户会觉得「AI 还在抢话」 |
| 2 | **停生成 / 停转发** | 服务端，可异步 | 有 cancel：~50ms；没有 cancel：立刻停**转发**，生成耗尽 | 带宽浪费；更糟的是迟到帧在错误的轮上被当成新回复 |
| 3 | **修上下文** | 两边 | ~10ms 量级的记账 | 模型下一轮接着没被听到的句子写；转录变成假学习资产 |

三条是正交的。论证「1 必须本地」推不出「2、3 可以不做」。

VAD 检测本身大约 200ms。所以整条链路的体感几乎被「本地停播够不够快」决定，**不是**被 WSS 往返决定。任何「等服务端 ack 再静音」的方案都进不了这个预算 —— 方向 A 曾经把「停」做在服务端（不发音频），客户端那半反而没被当成主机制，真机直接静音。复盘的结论仍是：

> **stop playback client-side the instant barge-in is detected — the server round-trip is for context reconciliation, not for stopping audio.**

9/12 的修法遵守这条：`interruptNow()` 仍然是主停播；网关新增的是 2（停转发）和 3（`deliveredText` + `interrupted`）。没有把静音改回等网关。

## ④ 标杆实现怎么接线

### 4.1 OpenAI Realtime（消息型，和本项目最近）

三件套，**不是**一个 `interrupt` 帧包打天下：

| 帧 / 调用 | 对应上表 |
|---|---|
| `output_audio_buffer.clear` | 1. 清客户端已排未播的 PCM |
| `response.cancel` | 2. 停这一轮生成 |
| `conversation.item.truncate`（带 `audio_end_ms`） | 3. 把这条 assistant item 截到用户**实际听到**的毫秒 |

他们明确写：barge-in 之后**还会有几帧在途**，客户端必须丢弃；`onInterrupted` 的含义是「从这一点起，被取消的那一轮不应再有帧」。那就是轮次归属。音频帧如果自己不带轮次键，就必须另有水位线或 truncate 点。

本项目没有 `audio_end_ms`。代理是网关记下的 `deliveredText`（与 TTS 同源推进）。诚实上限是「网关送出了什么」，不是「耳膜收到了什么」—— 差着水位线丢掉的那几帧。从「整段回复」改成「打断点之前」，是没有播放头上报时唯一可做的截断。

### 4.2 LiveKit Agents / Pipecat 一类编排框架

用户开始说话的事件（`user_started_speaking` / `BotInterrupted`）会：

- 取消当前 TTS 播放任务（本地）
- 取消或打断 LLM 的当前 response（有 API 就 cancel，没有就丢弃后续 frame）
- 用「最小打断时长」滤掉咳嗽、单音节误触

它们把音频当成**带类型的 frame 流**（`AudioRawFrame`、`BotStartedSpeakingFrame`），打断是流上的控制帧，不是在 HTTP 往返里另开一条「打断 API」。这和本项目「同一条 WSS 上 JSON + 二进制」是同一家族，只是他们把归属放在 frame 自己的元数据里，而本项目的二进制帧**没有** `turn_id`（见 97）。

### 4.3 电话 / IVR（Dialogflow CX、Amazon Connect、Twilio ConversationRelay）

电话更早遇到这个问题，因为播放缓冲在交换机或媒体服务器上，比手机多一跳。常见旋钮：

- `bargeIn=true`：检测到语音就停提示音
- 播放进度用 **DTMF 或媒体时间戳** 回传，而不是「生成完毕」
- 明确区分 `no-input` / `no-match` / `barge-in`

电话侧几乎从不会用「TTS 文件生成完」当「用户听完」——那会让 30 秒提示在第 3 秒被打断后，系统仍以为整段播过了。本项目 9/12 之前的转录，正是这个电话业界 20 年前就拒绝的形状。

### 4.4 Gemini Live / Amazon Nova Sonic 一类「端到端 duplex」

供应商自己做 barge-in：麦克风一直开，模型在音频层面抢话。客户端仍然必须本地静音，否则喇叭漏进麦克风会自激。

本项目**没有**走这条。90 写过：消息级而非媒体级，省掉 AEC、混音、双路时钟。代价就是 barge-in 必须由**应用协议**来做 —— 也就是 95 修的那些帧顺序和停转发。不能指望火山在 PCM 里听见用户而自动停；火山那条 duplex 甚至没有公开 cancel。

### 4.5 共识里本项目做不到的那一项

几乎所有标杆的第 2 步都包含 **cancel 上游**。本项目核实过：火山 Duplex **没有** cancel API。所以第 2 步在这里退化成：

- 停**转发**（手机不再听到尾巴）
- 继续**读完**上游事件（把残留 `response.done` 消化在本轮 collect 里，避免 95 §5.1）
- 账单仍按上游 PCM

这不是没做到业界，是供应商边界。文档必须把「停听到的」和「停账单」分开写，否则下一个人会再去找一个不存在的 cancel 调用。

## ⑤ 原理：三条时钟，四个不变量

把标杆抽象成四条，任何长 TTS 对话系统都得选边。

### 5.1 播放完成 ≠ 生成完成

TTS 是「先全部生成、再慢慢播」还是「边生成边播」，只改变散开的方向，不消除散开：

- 非流式：生成时钟先跑完，播放时钟从 0 开始排 15 秒。`turn.end` 若跟生成走，播放还剩 15 秒。
- 流式：生成和转发几乎一起走，播放仍落后一个缓冲。长句仍然能落后十几秒。

**谁先结束，不能当谁已经发生。** `ai.turn.end`、`response.done`、`output_audio.done` 说的是不同时钟。

### 5.2 在途帧是特性，不是 bug

打断那一刻，网关、内核、客户端队列里都有已经发出、尚未播放的 PCM。标杆的原话是 expect a few in-flight frames。处理它们的办法是**丢弃并标记「从此该轮不再来帧」**，不是假装连接上突然安静。

本项目用两道水位线（传输层 `AudioFrameDropGate`、播放层 `AudioPlaybackGate`）丢「序号 ≤ 打断点」的帧。它们**挡不住更高序号的下一轮音频**，也**挡不住** `ai.turn.end` 之后才到的尾巴被当成新气泡 —— 那是帧语义问题，不是闸门灵敏度问题。

### 5.3 轮次归属必须有一个不会被「下一轮开口」洗掉的锚

OpenAI 用 `item_id` + `audio_end_ms`。LiveKit 用 frame 上的 speech id。本项目二进制帧没有 `turn_id`，锚是：

- 网关：`activeTurnID` + `interruptedThisTurn` + `deliveredText`
- 客户端：`userTurnCount` 解释 `ai.turn.end` 的两种意思（94）+ 水位线

9/12 之前 `user.speech.start` 会 `resetTurnStreamingState()`，等于用「下一轮的开口」擦掉「上一轮的听到了什么」。锚不能活在会被下一轮 start 清零的那块状态里 —— 除非 start 能区分「collect 还在飞」和「新的一轮」。

### 5.4 UI 封口的那条帧，不能晚于该轮最后一字节音频，也不能早于

这是 5.1 的操作化：

- **早于**：尾巴音频变成新气泡（95 §4.1）
- **晚于**：状态机停在「AI 在说话」，评价 / 超时会按错误相位开火

所以收尾顺序不是审美，是「封口帧」和「最后一字节」的偏序。

## ⑥ 原来的代码：不是一处 if，是四条不变量都空着

「改动不少」的观感来自：一个手势同时打在四条空不变量上。每一处原来都有一个当时成立的理由，叠在长 TTS 上就不成立。

### 6.1 「interrupt 只打日志」—— 把 1 的理由用成 2、3 的豁免

87 的论证：200ms 只有端上做得到。结论被写成网关两层空操作。

**当时成立的部分**：不要等上游 ack 再静音。  
**不成立的外推**：于是转发可以继续、转录可以记整段、读循环可以同步卡在 collect 上。

代码形状：`HandleClientControl(interrupt)` 置完日志返回 `nil, nil`；sink 无条件 `emit`。长 TTS 时手机已经停播，WSS 上仍在灌更高序号的帧；水位线只丢 ≤ 旧序号，**新序号照播**，直到 `stopCapture` 或下一轮 `interruptNow`。更糟的是这些帧若落在 `ai.turn.end` 之后，会开新气泡。

### 6.2 「`ai.turn.end` = 这一轮在 UI 上结束」—— 用生成时钟驱动播放时钟的 UI

状态机在 `ai.turn.end` 上封气泡、切 `.processing` / `.evaluation`。这在「音频与 turn.end 同时到」的短回复上几乎看不出来。长回复上，生成结束比播放结束早十几秒，于是：

- 评价 20s 计时和播放并行（曾经用超时去停播，把句尾切掉，见 iOS `docs/47`）
- 用户在评价阶段开口，机器认为「服务端轮次已结束」，只本地停播，不发 `interrupt`
- 尾巴音频若在 turn.end 之后到，气泡裂开

原来把 `ai.turn.end` 同时当成「模型说完了」和「用户听完了」。这是两个命题。

### 6.3 「读循环里同步等 collect」—— 把一条连接当成单工 RPC

WSS 的价值就是**在等待一轮结果时仍能收控制帧**。把 `WaitTurnResult` 放进读循环，等于把双向管道用成「请求-响应」。短回复还好；长 TTS 生成期间 `interrupt` / `ping` 全部排队。这不是性能优化遗漏，是把 83 选 WSS 的理由在实现里又否决了一次。

### 6.4 「`user.speech.start` = 新一轮开始」—— 开口事件兼了复位

复位流式标记，在「上一轮已经干净结束」时正确。长 TTS 的 barge-in 发生时，上一轮的 collect 可能刚结束、也可能还在飞，播放一定还在。start 没有「是否正在 collect」的分支，于是打断记账被开口擦掉。`delivered_chars: 0` 是这个形状的签名，不是麦克风没拾到。

### 6.5 「`output_audio.done` ≈ 轮次结束」—— 音频流终结符当成会话终结符

火山的事件里，音频流有自己的 done，整轮 response 另有 done。用前者返回 collect，后者留在 socket 上，下一轮的第一口饭就是过期的 done。这是协议适配层把供应商的内部阶段泄漏成了本系统的轮次边界。

### 6.6 两条播放路径，打断只打中一条（加重，不是主因）

生产音频**不发** `ai.tts.start`，二进制帧走 `audioEngine.play`；`TTSFrameDispatcher` 保持 idle。`interrupt` 的副作用会 `ttsDispatcher.interrupt()`（对 idle 是空操作）+ `audioEngine.interruptNow()`（真正停播）。

这是历史事故：dispatcher 绑着只记账的 Mock 解码器，发 `ai.tts.start` 会让真声音消失。方向 A 回滚就是撞上这条。它不是气泡裂开的主因，但解释了为什么「协议上的 TTS 流」和「喇叭里的 PCM」不是同一个对象 —— 98 展开。

### 6.7 对照：原来缺的，对应业界哪一步

| 原来的代码 | 缺的不变量 | 业界对应 |
|---|---|---|
| interrupt 只打日志 | 停转发、修记录 | `response.cancel` 的退化版 + truncate |
| turn.end 封 UI | 封口不得早于最后一字节音频 | item 在 audio 完成后才 complete；或 complete 后拒绝再 append |
| 同步 collect | 等待时仍能收控制 | 同一条实时流上的 interrupt frame |
| start 总是 reset | 打断锚不被下一轮开口擦掉 | item_id 活过 user start |
| audio.done 结束 collect | 供应商内部阶段 ≠ 本系统轮次 | 只认上游的 response completed |
| 二进制无 turn_id | 迟到帧的归属 | frame metadata / truncate 点 / 水位线+封口顺序 |

改动面大，是因为这六行同时是空的；不是因为换了一种播放器或换了一条协议。

## ⑦ 这次改动刻意没有去做的

和 95 §⑦ 对齐，这里只补充**原理上的理由**：

**没有把停播改成等网关。** 那会违反 ③ 的预算。方向 A 已经用真机静音演示过反过来的代价。

**没有给音频帧加上 `turn_id`。** 那是对的长期方向（二进制头要改，v1 冻结），但 9/12 用「封口顺序 + 停转发 + 水位线」把当前协议下的归属补上了。加字段是下一轮版本化，见 84、97。

**没有在评价阶段发 WSS interrupt。** 服务端轮次已在 `response.done` 结束。再发会打在下一轮，正是 6.4 的形状。评价阶段只本地停播，与「1 必须本地、2 必须打在正确的轮上」同时成立。

**没有接上 `ai.tts.start` 那条会出声的解码器。** 那是另一张皮（98）。在归属还没钉住时接上，会把「没有声音」和「轮次错了」叠成一次无法拆的回归 —— 84 复盘写过这个流程错误。

### 7.1 补一条原理：作用面在「时序」，不在「语义」

84 记的是**回滚** —— 方向 A（网关发 `ai.tts.start` + 客户端接会出声的解码器）和方向 B（网关不发被打断那一轮的音频）都被撤了，真机静音。9/12 真正落地的修法只改**帧的先后**。两者差的不是手法，是**作用面**：

| 修法 | 改什么 | 失败模式 | 单元测试看得见吗 |
|---|---|---|---|
| 方向 B | 网关**送不送**字节 | 静音 | **看不见**（84 §3.4） |
| 方向 A | 客户端**走哪条**音频路径 | 静音 | **看不见** |
| 9/12 帧序 | 谁**先**发 | 转录截断点错 | **看得见** —— 断言帧序即可 |

**这是它成功的头一条理由**：时序层的错法可断言，语义层的错法（静音）在 `swift test` 里没有表示。修时序能在红验证里咬住，修语义只能上真机听。

第二条更硬：**语义层要新增的东西，恰恰是那个还不存在的锚。** 方向 A 发的 `ai.tts.start` 本质是 `turn_id` 的替身。锚没钉住就先接替身，静音与「轮次接错」会叠成一次拆不开的回归 —— 84 就是这么发生的。

所以顺序只能是：**先用时序把记账修对（可断言），再谈语义层的锚**。95 §4.2 复核后还多知道一件：连时序这道都非必需（网关守卫单独就够）。但它至少**安全** —— 它的错法只是「网上多一帧」，不是「没有声音」。

第三条：这次没有引入**新的「靠缺席成立」的关系**。84 §3.1 记的根本不协调是「音频能出声，正因为 `ai.tts.start` 缺席」。帧序改动不制造这种依赖。

## ⑨ 速查

| 项 | 值 |
