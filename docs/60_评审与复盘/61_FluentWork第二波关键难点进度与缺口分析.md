## 二、难点逐项分析

### 难点 1：语音链路火山做实（P0，最高优先）

**为什么最紧要**

1. 首响延迟是 PRD 设计原则第 5 条"产品生死线"，W1-W2 出口标准（首响 P90 ≤ 1.5s）是全局 Go/No-Go 阀门，至今未测；
2. `B12`（B7 命中检测）的技术路径依赖端到端注入能力 POC（技术方案 3.3 明确为"未验证假设"），POC 没跑，B12 无法定案；
3. 三个未验证假设集中在此：端到端注入窗口、中式口音 WER、外放 AEC 效果；
4. 商务前置未闭环（免费额度算账、企业协议"数据不用于训练"条款、并发配额合同），技术开工可能被卡。

**实现现状（代码证据）**

1. `fluentwork-backend/internal/voicegateway/handler.go`：`session.start` 返回 stub `ai.text.delta`（文本固定 "ready"），无任何火山调用；
2. `fluentwork-ios` DI 注入 `PlaceholderAudioEngine`（`AppDependencies.swift`），无真实采集 / Opus 编码 / 播放；帧编解码（`WSAudioFrameCodec`）已具备；
3. 三级降级切换逻辑、三段延迟埋点：均不存在。

**测试现状**

1. `internal/voicegateway/handler_test.go` 仅 2 个测试函数，只覆盖握手骨架；
2. `internal/voiceproto/frames_test.go` 覆盖帧编解码契约（可复用）；
3. iOS `SocketTransportTests` 覆盖帧收发与丢帧门（可复用）；真实音频回环、打断时延均无测试。

**防腐层（ACL）设计盘点（2026-08-29）**

结论：**外侧半层已就位，内侧供应商抽象不存在。**

| 层 | 现状 | 证据 |
|---|---|---|
| 客户端 ⇄ 网关（自有协议） | 已就位：自有 WSS 帧契约（`wss-control-frames-v1.json`）本身就是隔离带 | 帧契约 + 两端编解码测试 |
| iOS 音频能力抽象 | 已就位：`AudioEngineProtocol`（采集 / 打断语义）+ `PlaceholderAudioEngine` 占位，供应商无关 | `AppDependencies.swift` |
| iOS 传输抽象 | 已就位：`SocketTransportProtocol` + `InMemorySocketTransport` 测试替身 | `Shared/FluentWorkNetworking/Socket/` |
| 网关 ⇄ 单体内部边界 | 已就位：`TicketConsumer` / `SessionLifecycle` 接口 | `internal/voicegateway/` |
| **网关 ⇄ 火山（供应商抽象）** | **不存在**：无 `VoiceProvider` 类接口，stub 内联在 `handler.go`，协议适配无落点 | 全库无供应商接口定义 |

处置：`B13` 已更新——防腐层先行（`VoiceProvider` 接口 + 能力声明，火山与 mock 都是适配器），`handler` 主流程不允许出现火山专有类型；该要求已写入 `B13` 的 Scope / AC。

**模拟接入测试方案与评价标准现状**

- 已有可复用资产：`InMemorySocketTransport`（iOS 测试替身）、`frames_test.go` 契约测试模式、《`50_FluentWork端到端注入能力验证文档`》的用例 + 通过标准 + 报告模板方法论；
- 缺口：**无 `MockVoiceProvider`，无成文的语音链路模拟接入测试方案**；评价指标散落在各文档（首响 P90 ≤ 1.5s / 网关附加延迟 < 30ms / 打断 ≤ 200ms / 三级降级），未聚合为可执行方案；
- 处置：`B13` 已更新——随票交付 `MockVoiceProvider`（无真实凭证可跑）与模拟接入测试方案（用例集 + 评价标准：首响 / 转发延迟 / 打断 / 降级切换成功率 / 帧序列号完整性）。

**缺口与可补充项**

1. 立即启动 `B14` 注入 POC（不依赖网关，唯一可以马上开始的任务）；
2. `B13` 开工前先完成音频回环自测方案（坑清单 #3：接入第一天执行）；
3. 补网关测试：会话生命周期 + 降级切换契约测试（当前 2 个测试远不够）；
4. 推动商务三项前置，作为 `B13` 开工门禁写入执行记录；
5. 打断 200ms 指标需要端上测量方案（`I12` 验收时补）。

### 难点 2：review 评价 + 炼化真实现（P0）

**为什么紧要**

1. "说 → 读 → 入库"是 W5 出口标准，回顾页双栏对照是首次体验的最强 wow moment（PRD 风险表明确）；
2. 评价强制引用原句、炼化来自真实卡壳点，Prompt 质量直接决定产品可信度；
3. 代码库中没有任何 LLM 供应商客户端，`B8` 实际包含"从 0 建 AI 调用层"的工作量，容易被低估。

**实现现状（代码证据）**

1. 任务基建已完成且较扎实：`internal/session/review.go` 实现 claim / complete / fail（重试 1 次）/ 超时 detach；`cmd/worker/main.go` 可运行；幂等（`StatusReviewed` 直接跳过）已实现；
2. 内容生成为 `buildStubReviewJSON`（generator: `stub-v1`），只返回计数与占位摘要；
3. `ai_cost_logs` 表已建（migration 0002），但无任何写入路径；
4. `prompt_configs` 表未建，Prompt 管理未起步。

**测试现状**

1. `internal/session/service_test.go` 11 个测试，覆盖任务认领 / 重试 / 幂等（基建可信）；
2. `internal/session/http_test.go` 8 个测试，覆盖三态轮询接口；
3. 评价 / 炼化内容生成、JSON Schema 校验、成本落账：零测试（尚无实现）。

**成本监控（ai_cost_logs）专项盘点（2026-08-29）**

结论：**只有表，没有写入路径，更没有测试。**

1. migration 0002 已建 `ai_cost_logs` 表（含 `task_type` / `model` / `tokens_in` / `tokens_out` / `audio_sec` / `cost_fen`），建表注释明确"写入路径随 AI 调用落地接入"；
2. 后端 Go 代码对 `ai_cost_logs` 零引用：无写入、无查询、无单测；`embed_test` 仅验证 migration 存在；
3. 技术方案 3.2 要点 3 的纪律（"每次 AI 调用同步落一条，不允许后补"）目前没有任何实现承接；
4. 处置：`B8` 已更新——新增 cost recorder 组件（与结果同事务落账，"结果在、账必在"），并新增专项单测要求：`cost_fen` 单价计算 / 字段口径 / 同事务提交 / 重试不重复记账 / 写账失败视为任务失败不静默丢账；额度校验仍属 V1.1 不进本期。

**缺口与可补充项**

1. 先落最小 LLM 客户端（供应商、超时、重试、成本落账一体），避免散落在 worker 里；
2. JSON Schema 校验失败重试路径需要专项单测（技术方案硬要求"解析失败不进库"）;
3. 按技术方案 3.4，离线评估集（50-100 条标注样本）本应 W3 前建好，当前不存在——`B8` 开工应同步补，否则 Prompt 质量无回归手段；
4. 评价任务 P90 ≤ 15s 超时告警需要埋点落点设计；
5. `B9` 扩展全量模型时保持三态契约不回退（第一波测试资产可作回归基线）。

### 难点 3：语料库本地优先（P1，客户端典型难题）

**为什么紧要**

1. 语料库是产品护城河（PRD 14.2"用户语料库的累积效应"），弱网可浏览是 PRD 9.2 客户端专项要求；
2. `CorpusStore` / `SyncEngine` 涉及本地缓存与服务端增量同步的一致性设计，是第二波 iOS 侧唯一没有第一波经验可复用的新领域；
3. 入库是流水线终点，`batch-accept` 幂等与调度字段正确性影响后续闪测（下波次）数据质量。

**实现现状**

1. 两端均未开工：后端无 `corpus` 模块、无 `phrase_blocks` migration；iOS 无 `CorpusStore` / `SyncEngine`（`Shared/FluentWorkCore/Storage` 仅有 `SecureStorage`）；
2. 可复用基础：`SessionAPIClient` 的错误归一化模式、`NetworkMonitor` 弱网感知。

**测试现状**

- 无。弱网本地优先场景测试（32 号文档任务单 `C6` 验收项）尚无任何设计。

**缺口与可补充项**

1. 建议 `I9` 开工前先写一页同步策略定案（冲突口径、游标推进、删除语义），回写 `meta` 后再动代码；
2. 弱网测试可复用 `InMemorySocketTransport` 的 mock 思路建 mock API 层；
3. `batch-accept` 幂等键设计需要后端先行定契约（避免 iOS 等待）。

### 难点 4：B7 命中检测与注入时序（P1，被门禁卡住）

**为什么紧要**

1. 命中反馈是产品差异化核心（技术方案 3.3），且竞态设计复杂：端到端模型在 VAD 判停后几百毫秒内锁定上下文，旁路 800ms 注入多数情况只能影响"下下轮"；
2. 三档退路（当轮确认 / 下轮开局确认 / 仅徽章）必须由 `B14` POC 实测定档，目前档位未知，`B12` 与 `I11` 的 UI/交互设计都无法收敛。

**实现现状**

- 两端均未开工：网关无 `user.speech.end` 旁路触发点与检测链路；
- 第一波契约层已有准备：`wss-control-frames-v1.json` 已定义 `feedback.badge` 帧（第 99-103 行），iOS `WSControlFrame.feedbackBadge` 编解码已实现且有契约测试覆盖；真正缺的是网关检测旁路与触发逻辑；
- 话轮 `hit_block_ids` 字段已在 `utterances` 表预留（migration 0004），可直接使用。

**测试现状**

- 检测链路无测试；但契约测试框架（`frames_test.go` 模式）与 `feedback.badge` 帧编解码测试已存在，可直接复用。

**缺口与可补充项**

1. `B14` 是唯一解锁项，优先级应视为第二波事实上的第一张票；
2. 档位结论回写 `meta` 后，如需要在 `wss-control-frames-v1.json` 中补充档位语义 / 字段（帧契约本身已存在，无需新建）；
3. 800ms 超时 / 失败跳过的旁路纪律需要集成测试覆盖（不能让检测故障污染主链路）。

### 难点 5：回顾页两层到达时序（P2，容易被拖延的验收项）

**为什么列入**

1. 32 号文档任务单 `C5` 验收明确要"两层到达时序单测（骨架 → 内容）"，没有第一波现成模式可抄；
2. 渐进加载与轮询兜底（APNs 只加速、主动拉取兜底）的时序交叉容易出边界 bug。

**实现现状**

- iOS 已具备最小消费面：`SessionAPIClient.getSessionReview` + `ReviewPollResponse`、导航有 review 入口（`WorkspaceFeature` route `review`）；完整回顾 Feature 未开工。

**测试现状**

- 轮询接口有 `SessionAPIClientTests` 覆盖；两层到达时序无任何测试。

**缺口与可补充项**

1. `I7` 开工时先写时序单测骨架（骨架 → 评价/转录 → 炼化卡三个到达事件），再写 UI；
2. 失败态"重试"入口与轮询退避策略建议在 Feature 层统一定义，不散落在 View。

## 五、最终口径

第二波结束前的风险优先级应统一为：

1. 火山语音链路做实是第一优先（产品生死线 + 双重门禁 + 提审窗口）；
2. 评价/炼化的 LLM 链路是第二优先（W5 出口 + 工作量容易被低估）；
3. 语料库本地优先与命中检测紧随其后，且各自有"先定案再动码"的前置动作；
4. 测试补充与功能开发同步推进：网关测试、Schema 校验、弱网场景、时序单测是四个明确欠账。
