# 缺陷修复纪律:先复现,再修,留下守卫

**适用**:`fluentwork-ios`、`fluentwork-backend`、`fluentwork-infra`、`fluentwork-meta` 四仓。

## 目标

**任何"有人报告了一个问题"的修复,都必须留下一个曾经能复现它的测试。**

没有复现的修复不算修完 —— 那只是"看起来好了"。而且下一个改动会把它悄悄带回来。

## 强制顺序

1. **先写测试。** 一个在当前代码上会**失败**的测试。测试名描述**行为**,不是票号或日期。
2. **跑它,确认它失败。** 失败信息必须指向真实原因。**如果第一次就通过,说明你还没复现问题** —— 回到第 1 步,或者承认你猜错了。
3. **再改代码。** 只改到测试通过。
4. **跑全量门禁。** 确认没把别处改坏(旧契约被钉在别的测试里是常态,那就连同测试一起更新,并在实现说明里写明为什么旧契约不成立)。
5. **留下测试。** 它是这个缺陷的守卫,修完不许删。
6. **破坏实现,确认守卫咬得住。** 红的必须是**你预料的那条**;红的是别的、或者全绿,都说明你测错了东西 —— 见下一节。

## 守卫的守卫:改回去,看是哪条红

第 5 步留下守卫之后,还有一步**同样强制**:

> **破坏实现,再跑一次,看是哪条测试红。**

失败信息必须是你**预料的那条**。

| 结果 | 含义 |
|---|---|
| 红的正是预料的那条,失败信息说得清后果 | 守卫有效 |
| **红的是另一条** | **你对系统的理解有偏差** —— 去查为什么 |
| **没红 / 全绿** | **这条测试是空洞的** —— 它没有测到你以为它测的东西 |

### 它抓到过什么(全都是"测试通过"发现不了的)

| 场景 | 空洞在哪 |
|---|---|
| B17 的 nil-provider | 断言了 503,但另一条路径(`Collect` 自己也挡 nil)产出**逐字相同**的 503。**两条路径同一个症状时,断言症状的测试是盲的。** 真正能区分的是**顺序**(无守卫时畸形 body 先得 400) |
| 流式音频的重采样 | **「流式输出 == 整段输出」抓不住天真实现** —— 它永远只喂一块,而天真实现在"只喂一块"时与正确实现无法区分。只有**分块不变性**抓得住。**"等价性"测试看着更严格,对"边界"这个唯一失效维度却是盲的。** |

### 为什么这一步不能省

**"测试通过"不证明它测到了东西。** 一个空洞的守卫比没有守卫更糟:它给出的是**虚假的安全感**,而且会让人以为那片区域已经被覆盖。

**红验证的价值不在于"测试会红",而在于它会指出你测错了什么。**

## 为什么这条规则值得强制

本仓一个晚上的真机排查,三次都是这条链子把病因钉死的:

| 现象 | 先猜的结论 | 复现测试给出的真相 |
|---|---|---|
| 三轮后会话结束 | "供应商连接不稳" | `message too big: read limited at 32769 bytes` —— 读上限,与稳定性无关 |
| 每轮丢失上下文 | "记忆机制有问题" | 复现测试的失败信息就是用户看到的那条 `provider_audio_failed` 错误帧;根因是恢复路径每轮重开一条会话 |
| 单帧大音频 | "应该没问题" | 旧代码上 broken pipe —— 网关读侧也是 32 KiB 默认值 |

反过来,`partial` 掩盖读错误这条**藏了好几天**,正是因为当时没有测试去问"这个 `partial` 到底是超时还是断连"。

## 明确的例外

规则要能执行,就得说清什么时候不适用:

1. **新能力,没有"失败"可复现。** 例如新增一个协议字段、一个新的交互模式。此时写测试锁定**期望行为**,并在实现说明里写明「本票是能力新增,红/绿不适用」。
   例:`SpeechBoundaryMode` 增加 `.tapToStart` —— 旧代码上它是编译错误,不是测试失败。
2. **复现需要真机或供应商。** 先用**可注入的替身**复现:测试桩、假 WSS 服务器、可控失败的 provider。各仓已有这类脚手架,优先复用而不是新建。
   例:读上限用本地 mock WSS 发一个 96 KiB 帧即可复现,不需要真的连火山。
3. **确实无法自动化。** 在实现说明里写清**为什么不能**,以及**手动复现步骤**(命令、预期帧、预期日志行)。"测不了"不是省略的理由。

## 与实现说明的关系

实现说明里必须有一节「测试」,包含:

- **哪个测试**复现了这个缺陷(测试名)
- 它在**修复前的实际输出**(贴出来,不要转述)
- 修复后的门禁证据

## 机械检查(可选,但推荐)

凭据**可以被机械检查**:一个脚本,检查本次改动过的实现说明是否带上了「测试」一节。参考实现:

- `fluentwork-backend/scripts/check-defect-discipline.sh`(已接入该仓 `dev-check.sh`)

要移植的话,三条设计约束别丢:

1. **范围是工作区改动,不是全仓历史。** 本规则从某一刻起生效,之前的文档早于规则。追溯会让检查长期红着 —— **一个长期红的检查等于没有检查**。
2. **例外必须留出口。** 规则里的三类例外要么能通过检查(例如写明「红/绿不适用」即放行),要么检查会逼着人写假凭据,那比没有检查更糟。
3. **注意 git 的文件名转义。** 默认 `core.quotePath=true` 会把非 ASCII 文件名输出成带引号的转义串,路径随即失效。本仓文档名全是中文 —— 用默认输出的版本会对每一篇新文档**静默放行**。用 `-z`。

**它只能确认凭据在不在,确认不了诚不诚实。** 后者仍然是人看的。

## 边界

1. 本规则约束**缺陷修复**。纯重构、纯文档、格式调整不适用。
2. 它**不替代**仓库各自的门禁(build / test / lint),是门禁之前的第 0 步。
3. 它**不替代**人类 owner 对高风险目录的审查。
